# Story 4.1: Per-Job Budget Tracking

## Status

Approved

## Story

**As the** system  
**I need** to track spending per job  
**So that** costs don't exceed acceptable thresholds

## Acceptance Criteria

**DynamoDB job_budgets Table:**
1. Table created with partition key: job_id (String, UUID)
2. Fields: job_id, web_search_count (number, starts at 0), web_search_limit (number, default 10), estimated_cost_usd (running total, starts at 0), minimal_mode_activated (boolean, default false), tokens_used (running total, starts at 0), created_at (ISO timestamp), updated_at (ISO timestamp), last_cost_event_at (ISO timestamp, optional - for cost velocity tracking)
3. No sort key (single item per job_id)
4. No GSIs (not needed for per-job queries)

**Budget Initialization:**
5. When job starts, create job_budgets entry atomically (ConditionExpression: attribute_not_exists(job_id))
6. Set web_search_limit = 10 (normal mode)
7. Set estimated_cost_usd = 0
8. Set minimal_mode_activated = false
9. Set web_search_count = 0
10. Set tokens_used = 0
11. Set created_at and updated_at to current ISO timestamp

**Budget Updates (LLM Calls):**
12. **Budget mutation happens first; cost_event is emitted only after a successful budget update** (ensures budget is source of truth, decision events reflect committed state, retries don't double-log cost events)
13. After each LLM call: increment estimated_cost_usd and tokens_used atomically (UpdateItem with ADD)
14. Cost calculation: Use token usage from API response (prompt_tokens, completion_tokens) and model pricing
15. **After successful budget update:** Log cost_event decision event (from Story 3.1) with usd_estimate
16. Update job_budgets.estimated_cost_usd and job_budgets.tokens_used atomically
17. Update job_budgets.updated_at and job_budgets.last_cost_event_at to current ISO timestamp

**Budget Updates (Web Searches):**
18. After each web search: increment web_search_count atomically (UpdateItem with ADD, handled in Story 3.3)
19. Web search cost: Fixed cost per search from Tavily pricing plan
20. **After successful budget update:** Update job_budgets.estimated_cost_usd to include web search cost
21. Update job_budgets.updated_at and job_budgets.last_cost_event_at to current ISO timestamp

**Minimal Tool Mode Activation:**
22. **If estimated_cost_usd > $5**: Budget service activates minimal mode atomically
23. Budget service sets minimal_mode_activated = true (UpdateItem with ConditionExpression: estimated_cost_usd > 5 AND minimal_mode_activated = false)
24. Budget service sets web_search_limit = 2 (from 10 to 2)
25. Budget service emits cost_guardrail_triggered decision event (from Story 3.1)
26. Budget service updates job_budgets.updated_at to current ISO timestamp
27. Manager and Worker consume this state (do NOT manage it - read-only)

**Minimal Tool Mode Definition (Concrete):**
28. Minimal tool mode = **2 web searches TOTAL per job** (across all sub-workers, all iterations)
29. web_search_count tracks cumulative searches across entire job lifecycle (job-scoped, not iteration-scoped)
30. Budget enforcement is job-scoped, not iteration-scoped
31. **Budget service activates; Manager/Worker consume the constraint** (separation of concerns)
32. **Explicit rule:** If minimal_mode_activated = true AND web_search_count ≥ web_search_limit, no further web searches are permitted
33. **searches_remaining calculation:** `max(0, web_search_limit - web_search_count)` (prevents negative values, handles edge case where count exceeds limit)

**Budget Query API:**
34. Budget state queryable by job_id (GetItem from job_budgets table)
35. Budget state included in Worker context (web_search_limit, minimal_mode_activated, searches_remaining)
36. Budget state included in Manager context (estimated_cost_usd, minimal_mode_activated)
37. **searches_remaining** calculated as `max(0, web_search_limit - web_search_count)` (prevents negative values)

**Cost Warning (Non-Blocking Telemetry):**
38. **Optional enhancement:** At $2 threshold, log cost_warning_event decision event (non-blocking, just telemetry)
39. cost_warning_event includes: estimated_cost_usd, threshold ($2), warning_message
40. No behavior change at $2 (only logging for future dashboards and cost velocity tracking)
41. Can be deferred to Epic 5, but hook is planted now for future use

## Dev Notes

### Previous Story Insights

From Story 3.3 (Tool Usage Logging):
- Web search budget enforcement already implemented: Atomic reservation (UpdateItem with ConditionExpression BEFORE API call)
- Guardrail key: `job_id + iteration + sub_worker_type + sub_worker_instance_id` (for per-sub-worker-instance limits)
- **Note:** Story 3.3 uses per-sub-worker-instance limits (2 per instance), but Story 4.1 uses job-scoped limits (10 normal, 2 minimal mode TOTAL per job)
- **Integration:** Story 4.1's job-scoped web_search_limit (10 normal, 2 minimal) should be checked in addition to Story 3.3's per-instance limits

From Story 3.1 (Decision Event Capture):
- cost_event decision events already defined: event_type="cost_event", includes usd_estimate, tokens_used, provider, model
- cost_guardrail_triggered decision events already defined: event_type="cost_guardrail_triggered", includes budget_exceeded, minimal_mode_activated

From Story 2.1 (Manager Agent):
- Budget thresholds: warn at $2, fail at $5 (per-job, after accumulating cost)
- **Note:** Story 4.1 uses $5 threshold for minimal mode activation (consistent with Story 2.1)

**Key Insight:** Budget tracking is job-scoped (total cost per job), while web search limits in Story 3.3 are per-sub-worker-instance. Both must be enforced: Story 3.3's per-instance limit (2 per instance) AND Story 4.1's job-scoped limit (10 normal, 2 minimal mode TOTAL per job).

**Integration Note:** Story 3.3's AC 20 mentions "Budget counter in DynamoDB job_budgets table (key: job_id + iteration + sub_worker_type + sub_worker_instance_id)" but this conflicts with Story 4.1's job_budgets table schema (job_id only, no sort key). The per-instance limits in Story 3.3 should be tracked separately (e.g., in a separate table or as a nested structure). Story 4.1's job_budgets table tracks job-scoped totals only. Both limits must be checked before allowing web search.

### Technical Constraints

**Budget Initialization:**
- Must be atomic (ConditionExpression: attribute_not_exists(job_id)) to prevent duplicates
- Idempotent: If budget already exists, return existing budget (no error)

**Budget Updates:**
- **Budget mutation happens first; cost_event is emitted only after a successful budget update** (ensures budget is source of truth, decision events reflect committed state, retries don't double-log cost events)
- All updates must be atomic (UpdateItem with ADD for numeric fields)
- Minimal mode activation must be atomic (ConditionExpression: estimated_cost_usd > 5 AND minimal_mode_activated = false)
- Prevents race conditions: Multiple concurrent cost increments won't overshoot threshold
- **Explicit rule:** If minimal_mode_activated = true AND web_search_count ≥ web_search_limit, no further web searches are permitted
- **searches_remaining calculation:** `max(0, web_search_limit - web_search_count)` (prevents negative values, handles edge case where count exceeds limit)

**Cost Calculation:**
- LLM cost: Use token usage from API response and model pricing table
- Web search cost: Fixed cost per search from Tavily pricing plan
- Cost tracking happens after successful API calls (not on reservations)

**Minimal Mode Activation:**
- Threshold: $5 (consistent with Story 2.1)
- Activation is one-way (once activated, stays activated for job lifetime)
- web_search_limit changes from 10 to 2 atomically
- cost_guardrail_triggered event emitted (from Story 3.1)
- **Explicit rule:** If minimal_mode_activated = true AND web_search_count ≥ web_search_limit, no further web searches are permitted
- **searches_remaining calculation:** `max(0, web_search_limit - web_search_count)` (prevents negative values)

**Cost Warning (Non-Blocking Telemetry):**
- **Optional enhancement:** At $2 threshold, log cost_warning_event decision event (non-blocking, just telemetry)
- cost_warning_event includes: estimated_cost_usd, threshold ($2), warning_message
- No behavior change at $2 (only logging for future dashboards and cost velocity tracking)
- Can be deferred to Epic 5, but hook is planted now for future use

**Separation of Concerns:**
- Budget service manages budget state (activates minimal mode)
- Manager and Worker consume budget state (read-only, do NOT manage it)
- Tool wrappers enforce budget limits (Story 3.3)

**Integration with Story 3.3:**
- Story 3.3 enforces per-sub-worker-instance limits (2 per instance)
- Story 4.1 enforces job-scoped limits (10 normal, 2 minimal mode TOTAL per job)
- Both must be enforced: Check both limits before allowing web search
