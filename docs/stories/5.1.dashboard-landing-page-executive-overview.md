# Story 5.1: Dashboard Landing Page (Executive Overview)

## Status

Draft

## Story

**As an** AI developer  
**I want** a high-level overview of system performance  
**So that** I can quickly understand key metrics

## Acceptance Criteria

**Dashboard Landing Page:**
1. Dashboard page accessible at `/dashboard` route - **Security:** Public route but requires simple read token (dashboard token from env var) OR feature flag to hide sensitive data (cost/tokens/vendor split) - **MVP-safe options:** Keep route public but require dashboard token, or keep public but omit cost/tokens/vendor split until auth exists, or add `?mode=public` that strips sensitive fields - **If truly public, add feature flag to hide cost + tokens** (env var `DASHBOARD_HIDE_SENSITIVE=true`)
2. Page loads in <3 seconds (including data fetch)
3. Mobile responsive (works on 360px width minimum)
4. Uses Recharts library (lazy-loaded) for all chart visualizations
5. All metrics fetched from `/api/v1/dashboard/overview` endpoint (single API call for all metrics)

**Executive Overview Metrics (Top Section):**
6. **Total generations finished:** Display total number of finished jobs (count of summary records where `job_outcome IN ("completed", "failed")`) from `generation_metrics` table - **Note:** `generation_metrics.summary` must include `job_outcome` field (completed | failed) to distinguish terminal states
7. **Overall acceptance rate:** Display percentage with pie chart visualization:
   - Accept (distinct color, e.g., green): Percentage of jobs with `human_verdict = "accept"`
   - Would submit with edits (distinct color, e.g., yellow): Percentage of jobs with `human_verdict = "would_submit_with_edits"`
   - Would not submit (distinct color, e.g., orange): Percentage of jobs with `human_verdict = "would_not_submit"`
   - Reject (distinct color, e.g., red): Percentage of jobs with `human_verdict = "reject"`
   - **Note:** Colors are distinct and configurable (Recharts + theming); exact colors not hard-coded, legend required
8. **Most popular conference/topic combinations:** Display top 5 combinations in a table:
   - Columns: Conference, Topic, Count, Percentage
   - Sorted by count (descending)
   - **UI displays friendly labels** (e.g., "Black Hat USA", "GenAI"); **API uses snake_case enums** (e.g., "black_hat", "genai")
   - Data from `generation_metrics` table, aggregated by `request_context.conference` and `request_context.topic` (stored as snake_case in DB)
9. **Average generation time:** Display average end-to-end generation time in seconds (from `generation_metrics.summary.total_time_seconds`)
10. **Total cost and token usage:** Display running totals:
    - Total cost: Sum of `estimated_cost_usd` from all completed jobs
    - Total tokens: Sum of `tokens_used` from all completed jobs
    - Format: Cost as currency ($X.XX), tokens as formatted number (X,XXX,XXX)

**Acceptance Rate Trend Chart:**
11. Line chart showing acceptance rate over time (last 30 days by default, or all time if <30 days of data)
12. X-axis: Date (daily buckets)
13. Y-axis: Percentage (0-100%)
14. Separate lines for:
    - Accept (distinct color, e.g., green line)
    - "Would submit with edits" (distinct color, e.g., yellow line)
    - Combined (Accept + "Would submit with edits", distinct color, e.g., blue line)
15. Chart uses Recharts `LineChart` component (lazy-loaded)
16. Hover tooltip shows exact date, percentage, count, and **denominator (total jobs that day)** for each line
17. **Each day's data includes denominators:**
    - `total`: Number (total jobs finished that day)
    - `accept_count`: Number (jobs with `human_verdict = "accept"`)
    - `would_submit_with_edits_count`: Number (jobs with `human_verdict = "would_submit_with_edits"`)
    - `would_not_submit_count`: Number (jobs with `human_verdict = "would_not_submit"`)
    - `reject_count`: Number (jobs with `human_verdict = "reject"`)
18. Data fetched from `daily_metrics` table (precomputed) or aggregated from `generation_metrics` if daily metrics not available - **Fallback also uses last 30 days (not all time)**

**Vendor Performance Summary:**
18. 2x2 comparison table showing:
    - **OpenAI as Manager:**
      - **Submit-worthy rate:** Percentage of jobs with `manager_vendor = "openai"` and `human_verdict IN ("accept", "would_submit_with_edits")` - **Note:** This is "submit-worthy rate" (accept OR would_submit_with_edits), not "accept only"
      - Avg iterations: Average `iteration_count` for OpenAI Manager jobs
    - **Anthropic as Manager:**
      - **Submit-worthy rate:** Percentage of jobs with `manager_vendor = "anthropic"` and `human_verdict IN ("accept", "would_submit_with_edits")` - **Note:** This is "submit-worthy rate" (accept OR would_submit_with_edits), not "accept only"
      - Avg iterations: Average `iteration_count` for Anthropic Manager jobs
    - **OpenAI as Worker:**
      - **Submit-worthy rate:** Percentage of jobs with `worker_vendor = "openai"` and `human_verdict IN ("accept", "would_submit_with_edits")` - **Note:** This is "submit-worthy rate" (accept OR would_submit_with_edits), not "accept only"
      - Sub-worker spawn rate: Average `sub_worker_spawn_count` for OpenAI Worker jobs
    - **Anthropic as Worker:**
      - **Submit-worthy rate:** Percentage of jobs with `worker_vendor = "anthropic"` and `human_verdict IN ("accept", "would_submit_with_edits")` - **Note:** This is "submit-worthy rate" (accept OR would_submit_with_edits), not "accept only"
      - Sub-worker spawn rate: Average `sub_worker_spawn_count` for Anthropic Worker jobs
19. Table includes sample sizes (N) for each vendor-role combination
20. Data aggregated from `generation_metrics` table (summary records)

**Sub-Worker Usage Frequency:**
21. Bar chart showing count of times each sub-worker type spawned
22. X-axis: Sub-worker types (CFP Extractor, Evidence Researcher, Draft Generator, Red Team Reviewer)
23. Y-axis: Count (number of spawns)
24. Bars colored by sub-worker type (distinct colors)
25. Chart uses Recharts `BarChart` component (lazy-loaded)
26. Hover tooltip shows exact count and percentage of total spawns
27. **Metric semantics:** Data aggregated from `generation_metrics` table - **Recommendation:** Store `sub_worker_spawn_counts_by_type: {type: count}` object in summary record (best) OR explicitly define `sub_worker_types_spawned` as "one entry per spawn" (duplicates allowed) - **If unique set per job, chart becomes "jobs that used sub-worker type," not "spawn count"**

**Error Handling:**
28. If API returns no data (empty result): Display "No data available" message with helpful text
29. If API returns error: Display error message with retry button
30. Loading state: Show skeleton loaders for all metric cards and charts while data is fetching

**Performance:**
31. All charts lazy-loaded (dynamic import of Recharts components)
32. API response cached client-side for 5 minutes (prevent excessive API calls) - **Caching implementation:** Store `{data, fetchedAt}` in memory (and/or localStorage); if `now - fetchedAt < 5 min`, reuse data; bypass cache by ignoring timestamp check
33. Metrics refresh button available (manual refresh, bypasses cache)
34. **API performance constraint:** <2s aggregation may be unrealistic without pre-aggregation - **Note:** If scanning many summary records, consider `overview_metrics` table (single item updated daily/hourly) or extend `daily_metrics` to include vendor splits + sub-worker counts - **For MVP:** Fine to compute live if dataset is small; state "Uses last 30 days by default" or "If total records > X, rely on daily_metrics only"

## Dev Notes

### Previous Story Insights

From Story 1.1 (Landing Page & Conference Selection):
- Conference options: black_hat, reinvent, kubecon (snake_case)
- Topic options: genai, cybersecurity, containers, cloud_architecture, devops (snake_case)
- Request context stored in `request_context` field in jobs table

From Story 1.3 (Results Display & User Feedback):
- Human verdict values: "accept", "would_submit_with_edits", "would_not_submit", "reject"
- Verdict stored in `generation_metrics` table (summary records)

From Story 6.2 (DynamoDB Generation Metrics Storage):
- `generation_metrics` table stores summary records (PK: job_id, SK: record_type#timestamp where record_type = "summary")
- GSI2 (Summary Aggregation): PK: date_partition, SK: record_type#timestamp (optimized for aggregation queries)
- `daily_metrics` table stores precomputed daily aggregations (PK: metric_date, SK: metric_type#schema_version)
- Summary records include: `human_verdict`, `request_context`, `vendor_assignment`, `iteration_count`, `sub_worker_spawn_count`, `sub_worker_types_spawned`, `total_time_seconds`, `estimated_cost_usd`, `tokens_used`

**Key Insight:** Dashboard queries should use GSI2 for efficient aggregation queries. Daily metrics provide precomputed trend data, but dashboard should fallback to aggregating from `generation_metrics` if daily metrics not available.

### API Specifications

**Dashboard Overview Endpoint:**
- **Endpoint:** `GET /api/v1/dashboard/overview`
- **Authentication:** Simple read token (dashboard token from env var) OR feature flag to hide sensitive data - **MVP-safe options:** Require dashboard token, or keep public but omit cost/tokens/vendor split, or add `?mode=public` that strips sensitive fields
- **Response:** JSON object with all dashboard metrics (see Data Models section) - **Includes:** `generated_at` (ISO timestamp), `range: {start_date, end_date}` (date range used for trend and rollups)
- **Performance:** Response time <2 seconds (aggregation queries optimized using GSI2) - **Note:** <2s may be unrealistic without pre-aggregation; if scanning many records, consider `overview_metrics` table or extend `daily_metrics`; for MVP, fine to compute live if dataset is small (uses last 30 days by default)
- **Caching:** Client-side caching for 5 minutes (prevent excessive API calls)
- **Data range:** Uses last 30 days by default (or all time if <30 days of data) - **Fallback:** If `daily_metrics` not available, aggregate from `generation_metrics` (also last 30 days, not all time)

### Technical Constraints

**Performance:**
- Dashboard page load time: <3 seconds (including data fetch)
- API response time: <2 seconds (aggregation queries optimized using GSI2)
- Client-side caching: 5 minutes (prevent excessive API calls)

**Data Aggregation:**
- Use GSI2 (Summary Aggregation) for efficient queries on `generation_metrics` table
- Prefer `daily_metrics` table for trend data (precomputed), fallback to `generation_metrics` if not available
- Aggregate only summary records (record_type = "summary") from `generation_metrics` table

**Chart Library:**
- Use Recharts library (lazy-loaded via dynamic import)
- All charts must be responsive (adjust to container width)
- Charts must handle empty data gracefully (display "No data available" message)

**Mobile Responsiveness:**
- Dashboard must work on 360px width minimum
- Tables must be scrollable on mobile
- Charts must adjust to container width
