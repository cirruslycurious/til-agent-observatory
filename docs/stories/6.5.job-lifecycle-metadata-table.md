# Story 6.5: Job Lifecycle & Metadata Table

## Status

Draft

## Story

**As the** system  
**I need** centralized job lifecycle state tracking  
**So that** /status queries are cheap and job cleanup is automated

## Acceptance Criteria

**Table: jobs**

**Schema:**
1. Table created with partition key: job_id (String, UUID)
2. No sort key (single item per job_id)
3. No GSIs (not needed for per-job queries)
4. Billing mode: On-demand (low volume, predictable access patterns)
5. Point-in-time recovery: Enabled (for audit trail and data recovery)
6. TTL: `expires_at` field (Number, Unix timestamp, 7 days from creation) - DynamoDB auto-deletes expired items

**Attributes:**
7. `job_id`: String (UUID, partition key)
8. `job_read_token_hash`: String (HMAC-SHA256 hash of job_read_token with server secret) - Used for access control (prevents hash reuse if token generation weakens)
9. `status`: String enum (queued | running | completed | failed) - Current job state
10. `failure_reason`: String enum (nullable) - Failure reason if status = failed: timeout | validation_failed | budget_exceeded | internal_error | unknown
11. `created_at`: String (ISO timestamp) - Job creation time
12. `updated_at`: String (ISO timestamp) - Last status update time (set on every status transition)
13. `completed_at`: String (ISO timestamp, nullable) - Job completion time (set when status = completed or failed)
14. `last_heartbeat_at`: String (ISO timestamp, optional) - Last heartbeat from Step Functions (for detecting stuck jobs, optional for MVP)
15. `expires_at`: Number (Unix timestamp) - TTL for auto-cleanup (7 days from creation, configurable 7-30 days for MVP)
16. `request_context`: JSON object - Original request data:
    - `conference`: String (black_hat | reinvent | kubecon) - **snake_case for consistency**
    - `topic`: String (genai | cybersecurity | containers | cloud_architecture | devops) - **snake_case for consistency**
    - `user_session_id`: String (optional, for analytics)
17. `vendor_assignment`: JSON object - LLM vendor assignment:
    - `manager_vendor`: String (openai | anthropic)
    - `manager_model`: String (e.g., "gpt-4", "claude-3-opus")
    - `worker_vendor`: String (openai | anthropic)
    - `worker_model`: String (e.g., "gpt-4", "claude-3-opus")
    - `evaluator_model`: String (optional, e.g., "amazon.nova-pro-v1:0")
18. `error`: String (nullable, max 500 chars, truncated) - Short error message if status = failed (truncated to avoid leaking details)
19. `step_functions_execution_arn`: String (optional) - Step Functions execution ARN for job orchestration
20. `public_status`: JSON object (optional, stable API response shape) - Public-facing status fields:
    - `status`: String (queued | running | completed | failed)
    - `created_at`: String (ISO timestamp)
    - `completed_at`: String (ISO timestamp, nullable)
    - `error_code`: String (nullable, failure_reason enum value)

**Job Lifecycle States:**
17. **queued**: Job enqueued, waiting for Step Functions capacity (or initial state if SFN starts immediately)
18. **running**: Step Functions execution in progress (Manager → Worker → Evaluator → Manager state machine)
19. **completed**: Job finished successfully, results available (final abstract generated, evaluator assessment complete)
20. **failed**: Job failed (timeout, error, max retries exceeded, validation failure, budget exceeded)

**State Transitions:**
21. Create job: status = queued (if SFN at capacity) or running (if started immediately) - **Always emit `job_created` event, emit `job_started` event if status = running on create**
22. SFN starts: status = running (set when Step Functions execution starts) - **Only if current status is queued** (ConditionExpression: status = queued)
23. SFN completes successfully: status = completed, set completed_at = current timestamp - **Only if current status is running** (ConditionExpression: status = running)
24. SFN fails: status = failed, set completed_at = current timestamp, set error = error message (truncated to 500 chars), set failure_reason - **Only if current status is running** (ConditionExpression: status = running)
25. All state transitions update `updated_at` = current ISO timestamp
26. All state transitions logged as decision events (from Story 3.1): `job_created`, `job_started`, `job_completed`, `job_failed`
27. **Conditional updates prevent regression:** Use ConditionExpression in UpdateItem to prevent moving status backwards (e.g., only set running if status = queued, only set completed/failed if status = running)

**Benefits:**
26. **/status endpoint queries jobs table only** (cheap, no scanning event streams or aggregating from multiple tables)
27. Job metadata centralized (token, status, context, vendors) - single source of truth for job state
28. Automatic cleanup via TTL (7 days - configurable 7-30 days for MVP) - DynamoDB auto-deletes expired items
29. Failed job tracking (can retry or investigate) - status = failed with error message
30. Token verification: Query jobs table, compare hashed token (from Story 1.1)

**Access Patterns:**
31. Get job status: Query jobs table by job_id (GetItem, cheap and fast)
32. Verify token: Query jobs table by job_id, compute HMAC-SHA256(server_secret, provided_token), compare with job_read_token_hash
33. List failed jobs: Scan jobs table with filter status = failed AND created_at >= (now - N days) - **Bounded scan by date filter** (admin/debug only, low volume) - **Note:** If admin scan becomes common, add GSI on status + created_at
34. Job creation: PutItem with ConditionExpression: attribute_not_exists(job_id) - **Note:** UUID collisions are extremely rare; ConditionExpression is defensive but not true idempotency. For true idempotency (e.g., user double-clicks), accept idempotency_key from client or implement server-side debouncing (optional for MVP)

**Retention:**
35. TTL: 7 days (configurable 7-30 days for MVP)
36. After expiry: DynamoDB auto-deletes job record (eventual, not immediate - deletion happens within 48 hours of expires_at)
37. **TTL vs 410 Gone semantics:**
    - If item missing → 404 Not Found (or 410 Gone, implementation choice)
    - If item exists but current_time > expires_at → return 410 Gone (treat as expired even if not yet deleted by TTL, makes token invalidation deterministic)
38. Artifact and event data remains (indefinite) for analysis (scratch_artifacts, decision_events_by_job, generation_metrics)
39. **Retention mismatch consequence:** Jobs expire but artifacts/events remain forever - may accumulate S3/DDB artifacts indefinitely even when jobs disappear. Artifacts retention policy is separate; may add TTL/lifecycle later.

**Integration Points:**
39. Story 1.1 (Landing Page): Job creation writes to jobs table, returns job_id and job_read_token
40. Story 1.2 (Workflow Visualization): /status endpoint queries jobs table for job status
41. Story 2.1 (Manager Agent): Step Functions updates jobs table status (queued → running → completed/failed)
42. Story 3.1 (Decision Event Capture): Job lifecycle events logged to decision_events_by_job table
43. Story 6.2 (Generation Metrics): generation_metrics table references job_id (generation_id == job_id)

### API Specifications

**Job Creation Endpoint:**
- **Endpoint:** `POST /api/v1/jobs`
- **Authentication:** None (public endpoint)
- **Request Body:**
  ```json
  {
    "conference": "black_hat | reinvent | kubecon",
    "topic": "GenAI | Cybersecurity | Containers | Cloud Architecture | DevOps"
  }
  ```
- **Response:**
  ```json
  {
    "job_id": "String (UUID)",
    "job_read_token": "String (random, 32+ characters, high entropy, only returned once on creation)"
  }
  ```
- **Idempotency:** Uses ConditionExpression: attribute_not_exists(job_id) (defensive, UUID collisions are extremely rare) - **Note:** For true idempotency (e.g., user double-clicks), accept idempotency_key from client or implement server-side debouncing (optional for MVP)

**Job Status Query Endpoint:**
- **Endpoint:** `GET /api/v1/jobs/{job_id}/status?token={job_read_token}`
- **Authentication:** job_read_token (hash verification)
- **Query Parameters:**
  - `token`: job_read_token (required, hash verified)
- **Response (stable public_status shape):**
  ```json
  {
    "status": "queued | running | completed | failed",
    "created_at": "String (ISO timestamp)",
    "completed_at": "String (ISO timestamp, nullable)",
    "error_code": "String (nullable, failure_reason enum value: timeout | validation_failed | budget_exceeded | internal_error | unknown)"
  }
  ```
- **Error Responses:**
  - 404 Not Found: Job not found (item missing)
  - 410 Gone: Job expired (item exists but current_time > expires_at, or item missing after TTL deletion)
  - 403 Forbidden: Invalid token

**Admin Endpoint (Failed Jobs):**
- **Endpoint:** `GET /api/v1/admin/jobs/failed`
- **Authentication:** Admin API key or IAM role
- **Response:** Array of failed jobs
- **Pagination:** Limit 100 jobs per request

### Technical Constraints

**Table Design:**
- PK: job_id (String, UUID)
- No sort key (single item per job_id)
- No GSIs (not needed for per-job queries)
- Billing mode: On-demand (low volume, predictable access patterns)
- TTL: expires_at field (7 days from creation, configurable 7-30 days for MVP)

**State Management:**
- Status enum: queued | running | completed | failed
- failure_reason enum (nullable): timeout | validation_failed | budget_exceeded | internal_error | unknown
- State transitions: queued → running → completed/failed
- **Conditional updates prevent regression:** Use ConditionExpression in UpdateItem to prevent moving status backwards:
  - Only set running if status = queued
  - Only set completed/failed if status = running
- All state transitions update `updated_at` = current ISO timestamp
- All state transitions logged as decision events (from Story 3.1)
- **Event timing:** Always emit `job_created` event on create; if status = running on create, also emit `job_started` event

**Token Security:**
- job_read_token_hash: HMAC-SHA256(server_secret, job_read_token) - **Prevents hash reuse if token generation weakens**
- server_secret: Stored in Parameter Store (encrypted, KMS key)
- Token only returned once (on job creation)
- Token verification: Compute HMAC-SHA256(server_secret, provided_token), compare with stored hash
- Expired jobs: Return 410 Gone if current_time > expires_at (even if item not yet deleted by TTL, makes token invalidation deterministic)

**Idempotency:**
- Job creation: ConditionExpression: attribute_not_exists(job_id) - **Defensive, UUID collisions are extremely rare**
- **Note:** For true idempotency (e.g., user double-clicks), accept idempotency_key from client or implement server-side debouncing (optional for MVP)
- Current approach: Each job creation generates new UUID, so ConditionExpression is defensive but not true idempotency

**Retention:**
- TTL: 7 days (configurable 7-30 days for MVP)
- After expiry: DynamoDB auto-deletes job record (eventual, not immediate - deletion happens within 48 hours of expires_at)
- **TTL vs 410 Gone semantics:**
  - If item missing → 404 Not Found (or 410 Gone, implementation choice)
  - If item exists but current_time > expires_at → return 410 Gone (treat as expired even if not yet deleted by TTL, makes token invalidation deterministic)
- Artifact and event data remains (indefinite) for analysis
- **Retention mismatch consequence:** Jobs expire but artifacts/events remain forever - may accumulate S3/DDB artifacts indefinitely even when jobs disappear. Artifacts retention policy is separate; may add TTL/lifecycle later.
