# Story 3.3: Tool Usage Logging

## Status

Approved

## Story

**As an** AI developer  
**I want** detailed tool usage logs with reasoning  
**So that** I can analyze autonomous tool selection patterns

## Acceptance Criteria

**Tool Call Logging (Every Call):**
1. Calling agent/sub-worker ID and vendor (actor, worker_id, worker_vendor)
2. Tool name (enum: dynamodb_lookup, web_search, ...) - extensible for future tools
3. Parameters sent (summary if large, full if <100 chars)
4. Results_summary (50-200 chars, NOT full results) - generated deterministically (top N result titles + one-line relevance conclusion, hard truncate to 200 chars, no model calls)
5. Full results stored in S3 via s3_tool_results_ref if >50KB (per-tool pointer in provenance.tool_calls[])
6. Reasoning for call (why this tool, why now) - max 200 chars
7. Tokens used (if applicable, 0 if not applicable for non-LLM tools)
8. Execution time (milliseconds)
9. Cost estimated (if applicable, 0 if not tracked) - DynamoDB lookups: 0 if not tracked (not "free", but effectively 0 for analysis)
10. Success status (success | timeout | error | budget_exhausted | skipped) - skipped if guardrails block before any attempt

**Tool Call Storage:**
11. Logged as decision event: `tool_called` (from Story 3.1) - **Canonical timeline source**
12. Stored in artifact provenance.tool_calls array (when artifact is written) - **Subset, may lag if no artifact written**
13. Artifact provenance.tool_calls MUST include tool_invocation_id that links to a tool_called decision event
14. Full tool results in S3, reference in provenance.tool_calls[].s3_tool_results_ref (if >50KB, per-tool pointer)
15. Tool call schema validation: All required fields present, results_summary 50-200 chars

**Cost Guardrail Enforcement:**
16. Web search tool reserves budget atomically BEFORE calling API (UpdateItem with ConditionExpression, not GetItem + compare)
17. Budget reservation: UpdateItem ADD web_search_count :one with ConditionExpression web_search_count < :limit
18. If ConditionExpression fails: budget_exhausted, do NOT call API, return structured error: {status: "budget_exhausted", error: "...", searches_used: N, limit: N}
19. If reservation succeeds: API call happens after successful reservation (atomic reservation prevents race conditions)
20. Budget counter in DynamoDB job_budgets table (key: job_id + iteration + sub_worker_type + sub_worker_instance_id)
21. Worker receives budget status in context (structured error passed through)
22. Logging: cost_guardrail_triggered event when budget hit (from Story 3.1)

**Tool Call Analysis:**
23. Tool call sequences queryable by job_id (order of calls with reasoning)
24. Tool effectiveness metrics (success rate, avg_time, avg_cost per tool)
25. Tool usage patterns aggregatable for dashboard analytics

### Technical Constraints

**Budget Enforcement (Atomic Reservation):**
- Budget reservation MUST happen BEFORE API call (atomic UpdateItem, not GetItem + compare)
- Guardrail key: `f"{job_id}#{iteration}#{sub_worker_type}#{sub_worker_instance_id}"`
- **Atomic reservation:** UpdateItem ADD web_search_count :one with ConditionExpression: `web_search_count < :limit` (limit = 2)
- If ConditionExpression fails: budget_exhausted, do NOT call API, return structured error, log cost_guardrail_triggered event
- If reservation succeeds: API call happens AFTER successful reservation (prevents race conditions)
- **Note:** If API call fails (timeout/error), budget count is NOT refunded (keep it simple, log timeout/error)
- Max 2 web searches per sub-worker instance per iteration

**Tool Call Logging:**
- All tool calls logged as `tool_called` decision events (using shared event logger from Story 3.1) - **Canonical timeline source**
- Tool call records stored in artifact provenance.tool_calls array - **Subset, may lag if no artifact written**
- **Linking rule:** Artifact provenance.tool_calls MUST include tool_invocation_id that links to a tool_called decision event
- Results_summary: 50-200 chars (enforced validation, generated deterministically: top N result titles + one-line relevance conclusion, hard truncate to 200 chars, no model calls)
- Reasoning: Max 200 chars (enforced validation)
- Full results >50KB: Stored in S3, s3_tool_results_ref in provenance.tool_calls[].s3_tool_results_ref (per-tool pointer, not in artifact.overflow)

**S3 Integration:**
- Full tool results fetched from S3 on-demand (lazy loading)
- S3 key format: `tool-results/{job_id}/{tool_invocation_id}/results.json`
- SHA-256 hash verification: Verify payload_sha256 matches downloaded content

**Performance:**
- Tool call queries: Query decision_events_by_job table by job_id, filter by event_type="tool_called"
- Sort by sort key (timestamp#event_type#seq) for chronological order (use SK, not timestamp parsing)
- Query performance: O(n) where n = number of tool calls per job (typical: 5-15 tool calls)
- API pagination: Limit 100 tool calls per request
