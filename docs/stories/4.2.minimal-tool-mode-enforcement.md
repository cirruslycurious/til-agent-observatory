# Story 4.2: Minimal Tool Mode Enforcement

## Status

Approved

## Story

**As the** system  
**I need** to enforce budget limits mechanically in tool wrappers  
**So that** models cannot exceed budgets even if they try

## Acceptance Criteria

**DynamoDB web_search_guardrails Table (Per-Instance Limits):**
1. Table created with partition key: guardrail_key (String, format: `{job_id}#{iteration}#{sub_worker_type}#{sub_worker_instance_id}`)
2. Fields: guardrail_key, web_search_count (number, starts at 0), web_search_limit (number, fixed at 2), created_at (ISO timestamp), updated_at (ISO timestamp), optional TTL (for cleanup)
3. No sort key (single item per guardrail_key)
4. No GSIs (not needed for per-instance queries)
5. **Purpose:** Track per-sub-worker-instance web search limits (2 per instance per iteration), separate from job-scoped limits in job_budgets table

**Web Search Tool Wrapper Logic:**
6. Budget check happens in Lambda tool wrapper, NOT in model compliance (enforcement is mechanical, not prompt-based)
7. **Dual budget enforcement:** Enforce BOTH Story 3.3's per-sub-worker-instance limit (2 per instance) AND Story 4.1's job-scoped limit (10 normal, 2 minimal mode TOTAL per job)
8. **Reservation ordering:** Reserve job-scoped limit FIRST (scarcer resource in minimal mode), then per-instance limit (prevents wasting per-instance capacity if job is already exhausted)
9. **Job-scoped limit reservation (atomic, no read-then-reserve):**
   - UpdateItem job_budgets table: ADD web_search_count :one, SET updated_at = :now
   - ConditionExpression: `attribute_exists(job_id) AND web_search_count < web_search_limit` (web_search_limit is 10 normal, 2 if minimal_mode_activated = true, from Story 4.1)
   - **ReturnValues: ALL_NEW** (to get updated values for searches_remaining calculation without another read)
   - If ConditionExpression fails: Perform lightweight GetItem for diagnosis:
     - If item missing: Return structured error: `{status: "error", error: "budget_not_initialized", limit_type: "job_scoped", suggestion: "Budget not initialized for this job", api_called: false}`
     - Else (budget exhausted): Return structured error: `{status: "budget_exhausted", error: "Web search budget exhausted for this job", searches_used: N, limit: N, limit_type: "job_scoped", suggestion: "Use DynamoDB conference data instead", api_called: false}`
   - **Note:** No read-then-reserve pattern; atomic conditional update is the authoritative gate
10. **Per-instance limit reservation (atomic, after job-scoped succeeds):**
    - Guardrail key: `f"{job_id}#{iteration}#{sub_worker_type}#{sub_worker_instance_id}"`
    - UpdateItem web_search_guardrails table: ADD web_search_count :one, SET web_search_limit = if_not_exists(web_search_limit, :limit), created_at = if_not_exists(created_at, :now), updated_at = :now
    - ConditionExpression: `attribute_not_exists(web_search_count) OR web_search_count < :limit` (limit = 2, treats missing as 0)
    - **ReturnValues: ALL_NEW** (to get updated values for per-instance remaining calculation without another read)
    - If ConditionExpression fails: Return structured error: `{status: "budget_exhausted", error: "Web search budget exhausted for this sub-worker instance", searches_used: N, limit: 2, limit_type: "per_instance", suggestion: "Use DynamoDB conference data instead", api_called: false}`
    - **Note:** If per-instance reservation fails, job-scoped reservation is NOT refunded. We accept wasted job-scoped tokens to preserve a single-pass, race-safe design and avoid compensating transactions. (Alternative: reserve per-instance first to reverse waste direction, but job-first preserves scarcer resource.)
11. **If both reservations succeed:** API call happens AFTER successful reservations
12. **Counter incremented BEFORE API call** (failed searches still count - documented behavior for cost protection)
13. **Structured error response:** Return structured error (not exception) so Worker can adapt strategy
14. **Success status:** success | timeout | error | budget_exhausted (no "skipped" status; budget_exhausted indicates API was not called)
15. **api_called flag:** Include `api_called: false` in response if budget_exhausted (indicates API was not attempted)
16. **Success status and api_called mapping:**
    - If status="budget_exhausted": api_called=false, no tool cost incurred, budget counts already incremented
    - If status in {timeout, error}: api_called=true, budget counts already incremented (not refunded)
    - If status="success": api_called=true, budget counts already incremented, tool cost tracked
17. **searches_remaining calculation:** Use ReturnValues: ALL_NEW from UpdateItem to compute searches_remaining = max(0, web_search_limit - web_search_count) without additional read (for both job-scoped and per-instance)

**Worker Context Integration:**
16. Worker prompt includes budget context: "Web searches remaining: {searches_remaining}" (from Story 4.1, calculated as max(0, web_search_limit - web_search_count))
17. **Minimal tool mode context:** If minimal_mode_activated = true, include "Minimal tool mode active. Limit: 2 web searches total for this job."
18. Worker must adapt strategy (use DynamoDB, be conservative) when minimal tool mode is active

**Minimal Tool Mode Trigger (from Story 4.1):**
19. When estimated_cost > $5, **budget service** (not Manager) sets minimal_mode_activated = true
20. Budget service updates web_search_limit from 10 to 2
21. Budget service emits cost_guardrail_triggered decision event
22. Worker notified via context: "Minimal tool mode active. Limit: 2 web searches total for this job."

**Concrete Definition:**
23. Minimal tool mode = 2 web searches TOTAL per job (across all sub-workers, all iterations)
24. Job-scoped limit, not iteration-scoped
25. **Explicit rule:** If minimal_mode_activated = true AND web_search_count ≥ web_search_limit, no further web searches are permitted (from Story 4.1)

**Integration with Story 3.3 and Story 4.1:**
26. Story 3.3's per-sub-worker-instance limit (2 per instance) tracked in web_search_guardrails table (separate from job_budgets)
27. Story 4.1's job-scoped limit (10 normal, 2 minimal mode TOTAL per job) tracked in job_budgets table (single item per job_id)
28. Both limits must pass before allowing web search
29. Guardrail key for per-instance limit: `job_id + iteration + sub_worker_type + sub_worker_instance_id`

### Previous Story Insights

From Story 4.1 (Per-Job Budget Tracking):
- Job-scoped budget tracking: web_search_count, web_search_limit (10 normal, 2 minimal mode), minimal_mode_activated
- Minimal mode activation: When estimated_cost_usd > $5, budget service sets minimal_mode_activated = true and web_search_limit = 2
- **Explicit rule:** If minimal_mode_activated = true AND web_search_count ≥ web_search_limit, no further web searches are permitted
- searches_remaining calculation: `max(0, web_search_limit - web_search_count)` (prevents negative values)
- Budget service functions: `get_job_budget(job_id)`, `increment_web_search_cost(job_id, cost_usd)`

From Story 3.3 (Tool Usage Logging):
- Per-sub-worker-instance limit: Max 2 web searches per sub-worker instance per iteration
- Guardrail key: `job_id + iteration + sub_worker_type + sub_worker_instance_id`
- Atomic reservation: UpdateItem with ConditionExpression BEFORE API call
- **Note:** Story 3.3's AC 20 mentions "Budget counter in DynamoDB job_budgets table (key: job_id + iteration + sub_worker_type + sub_worker_instance_id)" but this conflicts with Story 4.1's job_budgets table schema (job_id only, no sort key). Story 4.2 resolves this by creating a dedicated web_search_guardrails table for per-instance limits.

**Key Insight:** Story 4.2 enforces BOTH limits using separate tables:
1. **Story 3.3's per-sub-worker-instance limit:** 2 web searches per sub-worker instance per iteration (tracked in web_search_guardrails table, guardrail_key = `job_id + iteration + sub_worker_type + sub_worker_instance_id`)
2. **Story 4.1's job-scoped limit:** 10 normal, 2 minimal mode TOTAL per job (tracked in job_budgets table, job_id only)

Both limits must pass before allowing web search. Reservation ordering: job-scoped FIRST (scarcer resource), then per-instance (prevents wasting per-instance capacity if job is already exhausted). The enforcement is mechanical (in tool wrapper), not prompt-based. No read-then-reserve pattern; atomic conditional updates are the authoritative gates.
