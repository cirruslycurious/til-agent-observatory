**So that** I can understand task decomposition patterns

## Acceptance Criteria

**Dashboard Page:**
1. Dashboard page accessible at `/dashboard/sub-workers` route (public, same security as Story 5.1)
2. Page loads in <3 seconds (including data fetch)
3. Mobile responsive (works on 360px width minimum)
4. Uses Recharts library (lazy-loaded) for all chart visualizations
5. All metrics fetched from `/api/v1/dashboard/sub-workers` endpoint (single API call for all metrics)

**Artifact Quality Analysis:**
6. Table per sub-worker type showing quality metrics:
    - **CFP/Style Extractor:**
      - Avg confidence score: Average `sub_worker_summary.cfp_extractor.confidence` from `generation_metrics` summary record - **Canonical source:** `generation_metrics` summary record (denormalized `sub_worker_summary` field, written at job completion)
      - Avg examples analyzed: Average `sub_worker_summary.cfp_extractor.examples_analyzed` from `generation_metrics` summary record
      - Coverage: Comprehensive: Percentage of jobs with `sub_worker_summary.cfp_extractor.coverage = "comprehensive"`
      - Timeout rate: Percentage of jobs with `sub_worker_summary.cfp_extractor.timed_out = true` - **Canonical source:** `generation_metrics` summary record (denormalized field, not event queries)
      - Acceptance correlation: Point-biserial correlation coefficient between sub-worker confidence and final job submit-worthy outcome (accept OR would_submit_with_edits) - **Guardrails:** Compute only when N ≥ 30 and confidence has variance (stddev > 0.05), otherwise return null with note: "insufficient variance / insufficient N"
    - **Evidence Researcher:**
      - Avg confidence score: Average `sub_worker_summary.evidence_researcher.confidence` from `generation_metrics` summary record - **Canonical source:** `generation_metrics` summary record (denormalized field) - **Include timed out runs in confidence averages only if confidence exists (usually it won't for timed out runs)**
      - Avg sources per bundle: Average `sub_worker_summary.evidence_researcher.sources_count` from `generation_metrics` summary record - **Include timed out runs in averages (time_ms likely equals timeout duration)**
      - Web searches per run: Average `sub_worker_summary.evidence_researcher.web_search_calls` from `generation_metrics` summary record - **Definition:** Per job where evidence_researcher spawned, count tool_called where actor=sub_worker, sub_worker_type=evidence_researcher, tool_name=web_search, then average across those jobs - **Canonical source:** `generation_metrics` summary record (denormalized field, not event queries) - **Include timed out runs in averages**
      - Timeout rate: Percentage of jobs with `sub_worker_summary.evidence_researcher.timed_out = true` - **Canonical source:** `generation_metrics` summary record (denormalized field) - **Denominator:** `jobs_with_sub_worker` (spawned per definition) - **Numerator:** Those with `timed_out === true`
      - Acceptance correlation: Point-biserial correlation coefficient between sub-worker confidence and final job submit-worthy outcome - **Definition:** Point-biserial correlation == Pearson(confidence, outcomeBinary) where outcomeBinary = 1 if submit-worthy, 0 otherwise - **Guardrails:** Compute only when N ≥ 30 and confidence has variance (stddev > 0.05), otherwise return null with note: "insufficient variance / insufficient N" - **Implementation rules:** Only include rows where `confidence != null`; if confidence is missing (e.g., red_team_reviewer may not have confidence), correlation should be null with note
    - **Draft Generator:**
      - Avg candidates generated: Average `sub_worker_summary.draft_generator.candidates_count` from `generation_metrics` summary record - **Canonical source:** `generation_metrics` summary record (denormalized field) - **Include timed out runs in averages (time_ms likely equals timeout duration)**
      - Avg confidence score: Average `sub_worker_summary.draft_generator.confidence` from `generation_metrics` summary record - **Include timed out runs in confidence averages only if confidence exists (usually it won't for timed out runs)**
      - Style alignment avg: Average `sub_worker_summary.draft_generator.style_alignment` from `generation_metrics` summary record (if available) - **Include timed out runs in averages only if style_alignment exists**
      - Timeout rate: Percentage of jobs with `sub_worker_summary.draft_generator.timed_out = true` - **Canonical source:** `generation_metrics` summary record (denormalized field) - **Denominator:** `jobs_with_sub_worker` (spawned per definition) - **Numerator:** Those with `timed_out === true`
      - Acceptance correlation: Point-biserial correlation coefficient between sub-worker confidence and final job submit-worthy outcome - **Definition:** Point-biserial correlation == Pearson(confidence, outcomeBinary) where outcomeBinary = 1 if submit-worthy, 0 otherwise - **Guardrails:** Compute only when N ≥ 30 and confidence has variance (stddev > 0.05), otherwise return null with note: "insufficient variance / insufficient N" - **Implementation rules:** Only include rows where `confidence != null`; if confidence is missing (e.g., red_team_reviewer may not have confidence), correlation should be null with note
    - **Red Team Reviewer:**
      - Avg issues found: Average `sub_worker_summary.red_team_reviewer.issues_count` from `generation_metrics` summary record - **Canonical source:** `generation_metrics` summary record (denormalized field) - **Include timed out runs in averages (time_ms likely equals timeout duration)**
      - Hallucination catch rate: Percentage of jobs with `sub_worker_summary.red_team_reviewer.hallucination_flagged = true` - **Canonical source:** `generation_metrics` summary record (denormalized field) - **Denominator:** `jobs_with_sub_worker` (spawned per definition) - **Numerator:** Those with `hallucination_flagged === true` - **Missing hallucination_flagged counts as "not flagged"**
      - False positive rate: Percentage of issues flagged that were later determined to be false positives (optional, requires manual review data) - **Optional for MVP, display "Not yet available" with tooltip**
      - Timeout rate: Percentage of jobs with `sub_worker_summary.red_team_reviewer.timed_out = true` - **Canonical source:** `generation_metrics` summary record (denormalized field) - **Denominator:** `jobs_with_sub_worker` (spawned per definition) - **Numerator:** Those with `timed_out === true`

7. All metrics include sample size (N) for each sub-worker type - **Definition:** `sample_size === jobs_with_sub_worker` (always, enforced in tests) - **Also include:** `jobs_with_sub_worker` and `jobs_without_sub_worker` counts (for lift table)

    - Bars: Avg time saved vs. sequential (computed: if parallel: `parallel_wall_time = max(sub_worker_time_ms[])`, sequential baseline: `sum(sub_worker_time_ms[])`, `time_saved = baseline - parallel_wall_time` (clamp >=0), if sequential: `time_saved = 0`) - **Note:** This measures "idealized parallel benefit" but not queueing/overhead
    - **Canonical source for time_ms array:** If `generation_metrics.sub_worker_time_ms` is present (array aligned to spawned sub-workers), use it. Else derive array from `sub_worker_summary.*.time_ms` (collect all non-null time_ms values for spawned sub-workers) - **Don't mix unless you define precedence**
    - **Include in response:** `pattern_frequency` (count of jobs using this pattern) and `avg_parallel_wall_time_seconds` (for sanity checking)
    - Chart uses Recharts BarChart component (lazy-loaded)

    - Format: Indented list showing artifact flow (e.g., "Style profile → evidence bundle → draft candidates → review feedback")
    - Click: Navigate to job detail page to see full dependency graph
    - **Selection logic (deterministic):** Take the 5 most recent jobs in date range that include ≥2 artifact types and have provenance edges (from `provenance.sources[]` array with `source_pointer` references) - **Return them sorted newest → oldest** - **Include `example_selection_note` in notes[]:** "Dependency graph examples: 5 most recent jobs with ≥2 artifact types and provenance edges"
    - **Data source:** `scratch_artifacts` table - **Only fetch artifacts for small sample set (5 job_ids) for dependency graph examples, not broad queries**
12. Bottleneck identification: Which sub-workers delay most often:
    - Table showing sub-worker types sorted by average delay time (time from spawn to completion)
    - Columns: Sub-worker type, Avg delay time (seconds), Frequency of delays (>20s threshold for bottlenecks, >30s for near-timeout), Sample size (N)
    - **Definition:** Delay time = time from spawn event to completion event - **Use timestamps from `sub_worker_summary.<type>.time_ms` (denormalized) or decision_events_by_job spawn/completed events** - **Include timed out runs in avg_delay_time_seconds (time_ms likely equals timeout duration)** - **This makes bottleneck stats truthful**
    - **Note:** Lambda timeout is 30s, so delays >30s are "timeouts or downstream lag" - **Thresholds:** `bottleneck_threshold_seconds: 20` (for bottlenecks), `near_timeout_threshold_seconds: 30` (for near-timeout) - **Include in API response as constants** (so FE doesn't hardcode)
    - **Data source:** `generation_metrics` summary record (`sub_worker_summary.<type>.time_ms` field, denormalized)

**Cost-Benefit Analysis:**
13. Table showing ROI per sub-worker:
    - Columns: Sub-worker type, Avg tokens used, Avg cost (USD), Acceptance lift (percentage point increase in submit-worthy rate when sub-worker was used vs. not used), ROI score (computed metric)
    - **Tokens/cost attribution per sub-worker:** Use `sub_worker_summary.<type>.tokens_used` and `sub_worker_summary.<type>.cost_usd` (denormalized per-sub-worker fields) - **If not available for MVP, be explicit:** "Avg tokens/cost is job-level, not sub-worker-level" (but then ROI per sub-worker becomes misleading) - **Recommendation:** Add per-sub-worker resource signals to `sub_worker_summary` (tokens_used, cost_usd) - **If you can't log cost per sub-worker for MVP, track tokens only and compute cost from vendor pricing later, but dashboard wants USD, so better to log cost_usd at runtime**
    - **ROI score computation:** `(acceptance_lift_percentage_points) / (avg_cost_usd)` - **Higher is better** (percentage point lift per dollar spent) - **Division guard:** If `avg_cost_usd` is 0 or null, `roi_score = 0` and add note: "roi_score set to 0 when avg_cost_usd is 0 or unavailable" - **Prefer not-null metrics, so return 0 + note rather than null**
    - **Acceptance lift is observational:** Sub-workers may be spawned more often on harder jobs - **Add caveat in notes[]:** "Acceptance lift is observational; sub-workers may be spawned more often on harder jobs" - **Future improvement:** Add stratification (compare within same conference/topic and maybe same manager vendor)
    - Sortable columns: Avg tokens, Avg cost, Acceptance lift, ROI score
    - **Data source:** `generation_metrics` summary records (compare jobs with sub-worker type vs. without) - **Include:** `jobs_with_sub_worker` and `jobs_without_sub_worker` counts for each sub-worker type
14. "When NOT spawning sub-workers worked better" analysis:
    - Table showing cases where jobs without a specific sub-worker type had higher submit-worthy rates than jobs with that sub-worker type
    - Columns: Sub-worker type, Submit-worthy rate (with sub-worker), Submit-worthy rate (without sub-worker), Difference (percentage points), Sample sizes (N with, N without)
    - **Note:** This is counter-intuitive findings analysis - helps identify when sub-workers may be unnecessary or harmful
    - **Data source:** `generation_metrics` summary records (compare jobs with vs. without each sub-worker type)

**Error Handling:**

If API returns no data (empty result): Display "No data available" message with helpful text - **Helpful message:** "Run at least 20 jobs to unlock sub-worker analysis." - **Definition of "empty result":** `total_jobs_in_range === 0` (no summary records in date range) - **Not "all arrays empty" because filtered mode could legitimately return no patterns but still have quality metrics** - **Include `total_jobs_in_range` in API response so FE can decide empty-state cleanly:** if `total_jobs_in_range === 0` show "No data available..."

### Previous Story Insights

From Story 2.3 (Sub-Worker Spawning & Coordination):
- Sub-worker types: `cfp_extractor`, `evidence_researcher`, `draft_generator`, `red_team_reviewer` (snake_case enum)
- Sub-workers write artifacts to `scratch_artifacts` table with standard envelope structure
- Artifacts include `quality_signals.confidence`, `quality_signals.coverage`, and artifact-specific metrics
- Sub-workers have 30-second timeout (Lambda timeout)
- Sub-workers must write either completed or failed artifact within 30s

### API Specifications

**Sub-Worker Deep Dive Endpoint:**
- **Endpoint:** `GET /api/v1/dashboard/sub-workers`
- **Authentication:** Simple read token (dashboard token from env var) OR feature flag - **Same security as Story 5.1**
- **Query Parameters:**
  - `date_from`: YYYY-MM-DD (optional, default: 30 days ago) - **Dashboard range defaults to last 30 days**

- **Performance:** Response time <3 seconds (aggregation queries optimized using GSI2 on generation_metrics table and efficient queries on scratch_artifacts and decision_events_by_job tables)
- **Caching:** Client-side caching for 5 minutes (prevent excessive API calls)
- **Data range:** Uses last 30 days by default (or all time if <30 days of data)

### Technical Constraints

**Performance:**
- Dashboard page load time: <3 seconds (including data fetch)
- API response time: <3 seconds (aggregation queries optimized using GSI2 on generation_metrics table and efficient queries on scratch_artifacts and decision_events_by_job tables)
- Client-side caching: 5 minutes (prevent excessive API calls)

**Data Aggregation:**
- **Primary:** Use `generation_metrics` table (summary records, GSI2) for efficient aggregation - **Single-table query for <3s SLA**
- **Denormalized sub_worker_summary field:** At job completion, write compact sub-worker summary into `generation_metrics` summary record (includes confidence, coverage, examples_analyzed, sources_count, web_search_calls, candidates_count, style_alignment, issues_count, hallucination_flagged, time_ms, timed_out for each sub-worker type)
- **Secondary (optional, sample only):** Use `scratch_artifacts` table for dependency graph examples (limit to 5 job_ids, not broad queries) - **Get relevant job_ids from generation_metrics query first, then fetch artifacts for small sample set**
- **Tertiary (optional):** Use `decision_events_by_job` table only if timeouts/tool counts not denormalized (should be denormalized, so this is not needed)
- Aggregate only summary records (record_type = "summary") from `generation_metrics` table

**Chart Library:**
- Use Recharts library (lazy-loaded via dynamic import)
- All charts must be responsive (adjust to container width)
- Charts must handle empty data gracefully (display "No data available" message)
- **Dependency graph visualization:** May need custom tree component or alternative library if Recharts doesn't support tree graphs

**Statistical Calculations:**
- Acceptance correlation: Calculate point-biserial correlation coefficient between sub-worker confidence and final job submit-worthy outcome - **Guardrails:** Compute only when N ≥ 30 and confidence has variance (stddev > 0.05), otherwise return null with note: "insufficient variance / insufficient N"
- ROI score: `(acceptance_lift_percentage_points) / (avg_cost_usd)` (higher is better) - **Note:** Acceptance lift is observational (not causal); sub-workers may be spawned more often on harder jobs

**Mobile Responsiveness:**
- Dashboard must work on 360px width minimum
- Tables must be scrollable on mobile
- Charts must adjust to container width
