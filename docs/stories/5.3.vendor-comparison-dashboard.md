# Story 5.3: Vendor Comparison Dashboard

## Status

Draft

## Story

**As an** AI developer  
**I want** side-by-side vendor comparison metrics  
**So that** I can make informed vendor selection decisions

## Acceptance Criteria

**Dashboard Page:**
1. Dashboard page accessible at `/dashboard/vendors` route (public, same security as Story 5.1)
2. Page loads in <3 seconds (including data fetch)
3. Mobile responsive (works on 360px width minimum)
4. Uses Recharts library (lazy-loaded) for all chart visualizations
5. All metrics fetched from `/api/v1/dashboard/vendors` endpoint (single API call for all metrics)

**Manager Effectiveness Comparison:**
6. Side-by-side table comparing OpenAI vs. Anthropic as Manager:
    - **Submit-worthy rate:** Percentage of jobs with `manager_vendor = "openai"` or `"anthropic"` and `human_verdict IN ("accept", "would_submit_with_edits")` - **Note:** This is "submit-worthy rate" (accept OR would_submit_with_edits), not "accept only" - **Canonical source:** `generation_metrics` summary record (single source)
    - **Avg iterations to submit-worthy:** Average `iteration_count` for jobs that reached submit-worthy outcome (submit-worthy jobs only) - **Canonical source:** `generation_metrics` summary record
    - **Feedback quality score:** Average `manager_feedback.actionability_score` (1-5 scale, if available) - **Optional for MVP, display "Not yet available" with tooltip** ("requires manager_feedback schema, not collected in MVP")
    - **Citation specificity:** Percentage of manager feedback that includes `sections_cited` (if available) - **Optional for MVP, display "Not yet available" with tooltip**
    - **Evaluator agreement rate:** Percentage of jobs where `evaluator_agreement = true` (evaluator top-1 match equals request_context.conference) - **Truth label:** Match against request_context.conference (actual conference requested) - **Canonical source:** `generation_metrics` summary record (denormalized `evaluator_agreement` boolean field, copied from evaluation_results at job completion) - **Option A (recommended):** Denormalize into summary record for single-table query - **Option B (alternative):** Join to evaluation_results at query time (harder + slower)
    - **Sample size (N):** Count of jobs for each vendor - **Also include:** `total_jobs` and `submit_worthy_jobs` counts (not just rate + N) for auditability
7. Bar chart: Submit-worthy rate by vendor (with confidence intervals if N≥50) - **Confidence interval method:** Wilson score interval for proportions (cheap + robust) - **Only compute when N ≥ 50** - **Optional for MVP, focus on clear data presentation with caveats**
8. Scatter plot: Iterations × Submit-worthy rate (color by vendor) - **Daily buckets:** X-axis = avg iterations (submit-worthy jobs only) per day, Y-axis = submit-worthy rate per day, Color = vendor (openai | anthropic, snake_case enum) - **This makes it an actual trend/variance visualization** (30 points × 2 vendors = 60 points, not just 2 points)
9. **Statistical significance indicators:**
    - Show confidence intervals when sample size ≥50 (Wilson score interval for proportions, cheap + robust) - **Only compute when N ≥ 50** - **Optional for MVP**
    - Flag differences <5% as "Small difference - may not be significant" - **Conditional on sample size:** If N is small, everything is "maybe" (only flag when N ≥ 20)
    - Display sample sizes prominently for all comparisons
    - Add "insufficient data" labels when N <20 for a comparison - **Threshold:** `insufficient_data_threshold: 20`
    - **Design principle:** Prioritize shipping insights over statistical rigor, let data speak for itself with appropriate caveats

**Worker Effectiveness Comparison:**
10. Side-by-side table comparing OpenAI vs. Anthropic as Worker:
    - **Submit-worthy rate:** Percentage of jobs with `worker_vendor = "openai"` or `"anthropic"` and `human_verdict IN ("accept", "would_submit_with_edits")` - **Note:** This is "submit-worthy rate" (accept OR would_submit_with_edits), not "accept only" - **Canonical source:** `generation_metrics` summary record (single source)
    - **Avg sub-workers spawned:** Average `sub_worker_spawn_count` for each vendor - **Canonical source:** `generation_metrics` summary record
    - **Parallel execution rate:** Percentage of jobs with `parallel_executions > 0` for each vendor - **Canonical source:** `generation_metrics` summary record
    - **Tool diversity (avg per job):** Average count of unique tool types used per job - **Definition:** `tool_diversity_avg_per_job = avg(|unique(tool_calls_made[].tool_name)|)` by vendor - **Canonical source:** `generation_metrics` summary record - **Note:** If `tool_calls_made[]` isn't guaranteed, consider storing `tool_names_used: string[]` on the summary record
    - **Avg tokens used:** Average `total_tokens` for each vendor - **Canonical source:** `generation_metrics` summary record
    - **Sample size (N):** Count of jobs for each vendor - **Also include:** `total_jobs` and `submit_worthy_jobs` counts (not just rate + N) for auditability
11. Grouped bar chart: Sub-worker spawn frequency by vendor - **X-axis:** Sub-worker types (cfp_extractor, evidence_researcher, draft_generator, red_team_reviewer, snake_case enum, UI displays friendly labels), Y-axis: Count, Grouped by vendor - **Canonical source:** `generation_metrics` summary record (`sub_worker_types_spawned` array)
12. Radar chart: Tool usage patterns (DynamoDB vs. Web Search balance) - **Stable axes for MVP:** Tool types (dynamodb_lookup, web_search, other) - **snake_case enum, UI displays friendly labels** - **Values:** Percentage of tool calls, Separate lines for each vendor - **Note:** Keep axes stable (dynamodb_lookup, web_search, other) so radar doesn't break when new tools are added - **Canonical source:** `generation_metrics` summary record (`tool_calls_made[]` array)

**Cross-Role Analysis:**
13. 2x2 matrix showing submit-worthy rates for vendor combinations:
    - OpenAI-Manager + Anthropic-Worker: X% (submit-worthy rate)
    - Anthropic-Manager + OpenAI-Worker: Y% (submit-worthy rate)
    - OpenAI-Manager + OpenAI-Worker: Z% (submit-worthy rate, edge case, should be rare)
    - Anthropic-Manager + Anthropic-Worker: W% (submit-worthy rate, edge case)
14. Sample sizes displayed for each combination - **Also include:** `total_jobs` and `submit_worthy_jobs` counts for each combination
15. Best and worst combinations highlighted (highest and lowest submit-worthy rates) - **Only highlight when both combinations have N ≥ 20** (otherwise you'll highlight noise)
16. **Note:** Edge cases (same vendor for Manager and Worker) should be rare due to vendor randomization, but included for completeness - **Canonical source:** `generation_metrics` summary record (aggregate by `manager_vendor` + `worker_vendor` combination)

**Error Handling:**
17. If API returns no data (empty result): Display "No data available" message with helpful text - **Helpful message:** "Run at least 20 jobs to unlock comparisons."
18. If API returns error: Display error message with retry button
19. Loading state: Show skeleton loaders for all charts and tables while data is fetching

**UI/UX Requirements:**
20. Always show date range used (top right of page) - **From API response:** `range: {start_date, end_date}`
21. Always show sample sizes (N) in every card/table header
22. For "Not yet available" metrics: Show muted text + small info tooltip (e.g., "requires manager_feedback schema, not collected in MVP")
23. Display helpful "No data available" message: "Run at least 20 jobs to unlock comparisons."

**Performance:**
20. All charts lazy-loaded (dynamic import of Recharts components)
21. API response cached client-side for 5 minutes (prevent excessive API calls)
22. Metrics refresh button available (manual refresh, bypasses cache)

## Dev Notes

### Previous Story Insights

From Story 5.1 (Dashboard Landing Page):
- Vendor performance summary already includes submit-worthy rates and sample sizes
- Uses `generation_metrics` table (summary records, GSI2) for efficient aggregation
- Dashboard range defaults to last 30 days

From Story 2.1 (Manager Agent):
- Manager feedback includes `actionability_score` (1-5 scale, optional)
- Manager feedback includes `sections_cited` (optional)
- Manager evaluates Worker output and provides feedback

From Story 2.4 (Evaluator Agent):
- Evaluator agreement: `evaluator_agreement = true` if evaluator top-1 match equals `request_context.conference`
- Truth label: Match against `request_context.conference` (actual conference requested)
- Evaluator results stored in `evaluation_results` table

From Story 6.2 (DynamoDB Generation Metrics Storage):
- `generation_metrics` table stores summary records with vendor assignments, iteration counts, sub-worker data, tool usage, and outcomes
- `human_verdict` field stores outcome (accept, would_submit_with_edits, would_not_submit, reject)
- `sub_worker_spawn_count` and `parallel_executions` fields track worker effectiveness

**Key Insight:** Vendor comparison aggregates from `generation_metrics` table (summary records) and `evaluation_results` table (evaluator agreement). Focus on clear data presentation with caveats, not rigorous statistical testing.

### API Specifications

**Vendor Comparison Endpoint:**
- **Endpoint:** `GET /api/v1/dashboard/vendors`
- **Authentication:** Simple read token (dashboard token from env var) OR feature flag - **Same security as Story 5.1**
- **Query Parameters:**
  - `date_from`: YYYY-MM-DD (optional, default: 30 days ago) - **Dashboard range defaults to last 30 days**
  - `date_to`: YYYY-MM-DD (optional, default: today)
  - `conference`: black_hat | reinvent | kubecon (optional filter, snake_case enum)
- **Response:** JSON object with all vendor comparison metrics (see Data Models section) - **Includes:** `generated_at` (ISO timestamp), `range: {start_date, end_date}` (date range used for aggregation, defaults to last 30 days)
- **Performance:** Response time <3 seconds (aggregation queries optimized using GSI2 on generation_metrics table)
- **Caching:** Client-side caching for 5 minutes (prevent excessive API calls)
- **Data range:** Uses last 30 days by default (or all time if <30 days of data)

### Technical Constraints

**Performance:**
- Dashboard page load time: <3 seconds (including data fetch)
- API response time: <3 seconds (aggregation queries optimized using GSI2 on generation_metrics table)
- Client-side caching: 5 minutes (prevent excessive API calls)

**Data Aggregation:**
- Use `generation_metrics` table (summary records, GSI2) for efficient aggregation - **Single canonical source for all metrics**
- **Evaluator agreement:** Denormalize `evaluator_agreement` boolean into `generation_metrics` summary record at job completion (Option A, recommended) - **Avoids cross-table joins, keeps /api/v1/dashboard/vendors fast and deterministic**
- **Alternative (Option B):** Join to `evaluation_results` table at query time (harder + slower, not recommended)
- Aggregate only summary records (record_type = "summary") from `generation_metrics` table
- **Data access plan:** Query GSI2 by date_partition buckets, filter by optional conference in-memory, aggregate in one pass (manager stats, worker stats, cross-role combinations, subworker counts, tool usage distribution)

**Chart Library:**
- Use Recharts library (lazy-loaded via dynamic import)
- All charts must be responsive (adjust to container width)
- Charts must handle empty data gracefully (display "No data available" message)

**Statistical Significance:**
- Confidence intervals optional for MVP (if N>50, if feasible to compute)
- Focus on clear data presentation with caveats, not rigorous statistical testing
- Flag differences <5% as "Small difference - may not be significant"
- Display "insufficient data" labels when N <20

**Mobile Responsiveness:**
- Dashboard must work on 360px width minimum
- Tables must be scrollable on mobile
- Charts must adjust to container width
