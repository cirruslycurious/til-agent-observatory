## Acceptance Criteria

**Dashboard Page:**
1. Dashboard page accessible at `/dashboard/performance` route (public, same security as Story 5.1)
2. Page loads in <3 seconds (including data fetch)
3. Mobile responsive (works on 360px width minimum)
4. Uses Recharts library (lazy-loaded) for all chart visualizations
5. All metrics fetched from `/api/v1/dashboard/performance` endpoint (single API call for all metrics) - **Tier A metrics:** DynamoDB-only queries (jobs, decision_events_by_job, generation_metrics, job_budgets) - **Tier B metrics:** Cached data from DynamoDB tables (cold_start_metrics, health_indicators) - **All data returned inline in single response** - **Note:** Cold-start and health data are precomputed and cached in DynamoDB (not queried from CloudWatch in hot path)

**Timing Analysis:**
6. End-to-end generation time percentiles:
    - p50: X seconds (median)
    - p90: X seconds
    - p99: X seconds
    - **Target:** p90 < 120 seconds, p99 < 300 seconds
    - **Denominator:** Jobs with `job_status="completed"` in `jobs` table where `completed_at >= created_at` and both timestamps exist - **Data hygiene:** Only include jobs where `completed_at >= created_at` and both exist - **Timestamp storage:** All timestamps stored in UTC ISO-8601 format - **Exclude:** Jobs with missing timestamps or non-monotonic timestamps (completed_at < created_at) - **Expose:** `timing_sample_size` (included jobs) and `timing_excluded_count` (excluded jobs) in API response for sanity checking
    - **Canonical source:** `jobs` table (`created_at`, `completed_at` timestamps)
7. Breakdown by stage (grouped bar chart):
    - Manager goal formulation: Time from job `created_at` to first `manager_goal_formulated` decision event - **Rule:** If event missing, stage duration = null and exclude from percentile denominator
    - Worker execution planning: Time from first `manager_goal_formulated` to first `worker_plan_created` decision event - **Rule:** Use first occurrence of each event type - **Rule:** If event missing, stage duration = null and exclude from percentile denominator
    - Sub-worker execution (parallel): Max time across all sub-worker invocations (from `sub_worker_spawned` to `sub_worker_completed` decision events) - **Rule:** Sub-worker stage = max(sub_worker_completed.timestamp - sub_worker_spawned.timestamp) across all invocations - **Rule:** If no sub-workers spawned, stage duration = null and exclude from percentile denominator
    - Tool calls: Sum of tool call latencies (denormalized `tool_calls_total_latency_ms` in `generation_metrics` summary) - **Rule:** Tool calls stage = sum of all tool call latencies for the job, independent of overlap with other stages - **Rule:** If no tool calls, stage duration = 0 (not null)
    - Evaluator wait: Time from first `evaluator_requested` to first `evaluator_assessment_completed` decision event - **Rule:** Use first occurrence of each event type - **Rule:** If event missing, stage duration = null and exclude from percentile denominator
    - Manager evaluation: Time from first `evaluator_assessment_completed` to first `manager_iteration_selected` decision event - **Rule:** Use first occurrence of each event type - **Rule:** If event missing, stage duration = null and exclude from percentile denominator
    - **Canonical source:** `generation_metrics` summary record (denormalized stage timestamps and counts) - **Denormalized fields:** `t_manager_goal_formulated_ms`, `t_worker_plan_created_ms`, `sub_worker_max_duration_ms`, `sub_workers_spawned_count`, `sub_workers_completed_count`, `t_evaluator_requested_ms`, `t_evaluator_completed_ms`, `t_manager_iteration_selected_ms`, `tool_calls_total_latency_ms` - **Timestamp units:** All `t_*_ms` fields are offsets from job `created_at` in milliseconds (not absolute timestamps) - **Stage duration calculation:** Manager goal = `t_manager_goal_formulated_ms`, Worker planning = `t_worker_plan_created_ms - t_manager_goal_formulated_ms`, Sub-worker = `sub_worker_max_duration_ms`, Tool calls = `tool_calls_total_latency_ms`, Evaluator wait = `t_evaluator_completed_ms - t_evaluator_requested_ms`, Manager evaluation = `t_manager_iteration_selected_ms - t_evaluator_completed_ms` - **Note:** Stage durations are independent measurements and may overlap due to parallelism - **Label explicitly:** "Avg stage time (may overlap)" - **Chart:** Recharts BarChart (grouped, not stacked) with stage labels - **Chart displays:** `avg_time_ms` per stage - **Percentiles:** p50/p90/p99 shown in tooltip (or small table below chart) - **Reason:** Grouped bars better represent independent measurements; stacked implies they sum to a whole
8. Lambda cold start impact chart:
    - X-axis: Request sequence (1st request, 2nd request, etc. per Lambda function)
    - Y-axis: Latency (ms)
    - Series: Manager Lambda, Worker Lambda, Sub-Worker Lambda, Evaluator Lambda
    - **Target:** Cold start < 2 seconds, warm < 500ms
    - **Canonical source:** Cached precomputed data in DynamoDB `cold_start_metrics` table (updated every 5 minutes by scheduled Lambda) - **Included inline in main `/api/v1/dashboard/performance` response** - **NOT fetched from CloudWatch Logs Insights in hot path** - **Display:** "Last computed at" indicator with timestamp
    - **Note:** CloudWatch Logs Insights queries are multi-second to tens of seconds and can be throttled, so they cannot be in the <3s page-load hot path

**Cost Analysis:**
9. Total token usage trends (line chart over time):
    - X-axis: Date (daily buckets)
    - Y-axis: Total tokens (sum of `tokens_used` from `job_budgets` table)
    - Series: prompt_tokens, completion_tokens, total_tokens
    - **Canonical source:** `job_budgets` table aggregated by `created_at` date
10. Cost per generation by vendor combination (simplified visualization):
    - X-axis: Vendor combination (e.g., "openai+anthropic", "anthropic+anthropic")
    - Y-axis: Cost (USD)
    - Display: p50 (median), p90, p99, and outlier count per vendor combination - **Simplified approach:** Use stat cards or bar chart with error bars instead of full box plot - **Reason:** Recharts doesn't ship a first-class BoxPlot component; custom rendering threatens schedule - **Alternative:** If box plot is required, explicitly accept custom box plot component (and test carefully on mobile)
    - **Canonical source:** `generation_metrics` summary record (`total_cost_usd`, `manager_vendor`, `worker_vendor` fields)
    - **Chart:** Recharts BarChart with error bars (or custom box plot component if required)
11. Tool call costs breakdown (pie chart):
    - DynamoDB: $X (minimal, fixed cost per lookup)
    - Web search: $X (primary external cost, from Tavily API)
    - LLM API: $X (primary cost, from OpenAI/Anthropic/Bedrock)
    - **Canonical source:** `generation_metrics` summary record (denormalized `cost_by_provider` field: `{dynamodb_usd, web_search_usd, llm_api_usd}`) - **Denormalized at job completion:** Avoids heavy event scans in dashboard - **Chart:** Recharts PieChart component
12. Sub-worker token efficiency:
    - Metric: Tokens per acceptance (total sub-worker tokens / number of accepted iterations)
    - **Target:** < 50,000 tokens per acceptance
    - **Denominator:** Jobs with `selected_iteration` != null
    - **Numerator:** Sum of `tokens_by_component.sub_workers` from `generation_metrics` summary
    - **Canonical source:** `generation_metrics` summary record
13. Cost guardrail effectiveness:
    - How often triggered: Percentage of jobs where `cost_guardrail_triggered = true` in `generation_metrics` summary
    - Impact on quality: Acceptance rate when guardrail triggered vs. normal (compare `user_accepted` rates)
    - **Target:** Guardrail triggered < 10% of jobs, acceptance rate difference < 5%
    - **Canonical source:** `generation_metrics` summary record (`cost_guardrail_triggered`, `user_accepted` fields)

**Reliability:**
14. Success rate by component (gauges):
    - Manager: Percentage of jobs where `had_manager_success = true` (denormalized flag in generation_metrics) - **Denormalized field:** `had_manager_success` boolean flag computed at job completion - **Prefer positive signals:** Presence of `manager_iteration_selected` event, not absence of `manager_failed` - **Rule:** If field is null, exclude from denominator (component never ran)
    - Worker: Percentage of jobs where `had_worker_success = true` (denormalized flag in generation_metrics) - **Denormalized field:** `had_worker_success` boolean flag computed at job completion - **Rule:** If field is null, exclude from denominator (component never ran)
    - Sub-workers (aggregate): Percentage where `sub_workers_completed_count == sub_workers_spawned_count` (denormalized counts in generation_metrics) - **Denormalized fields:** `sub_workers_spawned_count`, `sub_workers_completed_count` computed at job completion - **Rule:** Compare counts: if spawned_count == completed_count, success; if completed_count < spawned_count, failure - **Rule:** If no sub-workers spawned, exclude from denominator
    - Evaluator: Percentage of evaluator requests that completed successfully (`evaluator_status="completed"` in `generation_metrics` summary) - **Denormalized field:** `evaluator_status` in generation_metrics summary - **Already using positive signal:** `evaluator_status="completed"` is correct
    - **Target:** > 95% success rate for all components
    - **Canonical source for dashboard aggregation:** `generation_metrics` summary record (denormalized flags and counts computed at job completion) - **Note:** `decision_events_by_job` remains canonical for debug/drill-down views, not dashboard aggregates
15. Failure patterns table (top 5 failure types with counts):
    - Columns: Failure Type, Count, Percentage, Last Occurrence
    - Failure types: Enum `{manager_failed, worker_failed, sub_worker_failed, evaluator_failed, tool_failed, timeout, budget_exceeded, unknown}` - **Denormalized field:** `failure_type` in generation_metrics summary (computed at job completion) - **Precedence rule if multiple failures occur:** budget_exceeded > timeout > component_failed (manager/worker/sub_worker/evaluator) > tool_failed > unknown - **Stable taxonomy:** Enum prevents fragmentation (e.g., "timeout" vs "Timeout" vs "timeout: evaluator") - **Canonical source for dashboard aggregation:** `generation_metrics` summary record (denormalized `failure_type` field) - **Note:** `decision_events_by_job` remains canonical for debug/drill-down views, not dashboard aggregates
16. Timeout analysis:
    - Sub-worker timeouts: Percentage of sub-worker invocations that timed out (`sub_worker_timeout = true` in `generation_metrics` summary or `sub_worker_timeout` decision event)
    - Evaluator timeouts: Percentage of evaluator requests that timed out (`evaluator_timeout = true` in `generation_metrics` summary)
    - Fallback strategy success: Percentage of timeouts where fallback strategy succeeded (e.g., retry with different model, skip evaluator)
    - **Target:** Timeout rate < 5%, fallback success > 80%
    - **Canonical source:** `generation_metrics` summary record and `decision_events_by_job` table
17. Retry frequency histogram:
    - X-axis: Number of retries (0, 1, 2, 3+)
    - Y-axis: Count of jobs
    - **Canonical source:** `decision_events_by_job` table (count `event_type="retry"` decision events per job)

**Health Indicators:**
18. Current system status: Enabled / Disabled (green / red indicator):
    - **Source:** System configuration flag (stored in DynamoDB `system_config` table or environment variable) - **Cached:** Server-side cached response (updated every minute by scheduled Lambda or on config change) - **Display:** Green badge if enabled, red badge if disabled - **Update:** Included inline in `/api/v1/dashboard/performance` response - **Optional polling:** FE can poll `/api/v1/dashboard/performance?include=health` for health-only updates (returns only health block, prevents heavy recompute) - **Note:** Avoid polling CloudWatch directly from FE to prevent hammering CloudWatch and reduce brittleness
19. Daily cost progress bar (current / $20 limit):
    - **Source:** Server-side cached CloudWatch metric `daily_cost_usd` (updated every minute by scheduled Lambda) - **Cached:** Stored in DynamoDB `health_indicators` table - **Display:** Progress bar showing current cost / $20 limit
    - **Color:** Green if < $10, yellow if $10-$15, red if > $15
    - **Update:** Included inline in `/api/v1/dashboard/performance` response - **Optional polling:** FE can poll `/api/v1/dashboard/performance?include=health` for health-only updates - **Note:** CloudWatch GetMetricData has limits and cost considerations; cache server-side
20. API rate limit usage (current / limit):
    - **Source:** Server-side cached CloudWatch metrics for API Gateway throttling (updated every minute) - **Cached:** Stored in DynamoDB `health_indicators` table - **Display:** Progress bar showing current requests / rate limit
    - **Update:** Included inline in `/api/v1/dashboard/performance` response - **Optional polling:** FE can poll `/api/v1/dashboard/performance?include=health` for health-only updates - **Note:** Requires API Gateway metrics or custom tracking
21. Lambda concurrency usage (current / reserved):
    - **Source:** Server-side cached CloudWatch metrics for Lambda concurrent executions (updated every minute) - **Cached:** Stored in DynamoDB `health_indicators` table - **Display:** Progress bar showing current concurrent executions / reserved concurrency
    - **Update:** Included inline in `/api/v1/dashboard/performance` response - **Optional polling:** FE can poll `/api/v1/dashboard/performance?include=health` for health-only updates - **Note:** Requires Lambda reserved concurrency configuration

## Dev Notes

### Previous Story Insights

From Story 5.1 (Dashboard Landing Page):
- Dashboard security: Public endpoint (same as Story 5.1)
- Performance target: <3 seconds page load
- Mobile responsive: 360px width minimum
- Recharts lazy-loading: Use dynamic import for chart components

From Story 6.2 (DynamoDB Generation Metrics Storage):
- `generation_metrics` table: Contains summary records with aggregated metrics
- `job_budgets` table: Contains cost and token usage per job
- `decision_events_by_job` table: Contains chronological event timeline for stage breakdown

From Story 3.1 (Decision Event Capture):
- Decision events: Stored in `decision_events_by_job` table with chronological ordering
- Event types: `manager_goal_formulated`, `worker_plan_created`, `sub_worker_spawned`, `sub_worker_completed`, `tool_called`, `evaluator_requested`, `evaluator_assessment_completed`, `manager_iteration_selected`, `manager_failed`, `worker_failed`, `sub_worker_failed`, `evaluator_failed`, `tool_failed`, `timeout`, `budget_exceeded`, `retry`, `cost_event`
- Event timeline: Can reconstruct job timeline from decision events

From Story 4.1 (Per-Job Budget Tracking):
- `job_budgets` table: Contains `estimated_cost_usd`, `tokens_used`, `created_at`, `updated_at`
- Cost tracking: Cost events logged to `decision_events_by_job` table with `event_type="cost_event"`

From Story 3.3 (Tool Usage Logging):
- `tool_usage_logs` table: Contains tool invocation details with `tool_invocation_id`, `latency_ms`, `provider`
- Tool costs: Tracked in `cost_event` decision events with `provider` field

**Key Insight:** System performance dashboard requires aggregating data from multiple sources, but all data is returned in a single API call:
- **Primary data sources (DynamoDB):**
  - `jobs` table: End-to-end timing
  - `generation_metrics` summary: Stage breakdown (denormalized timestamps), cost per generation, sub-worker efficiency, guardrail effectiveness, tool latency sums, tool costs (denormalized), success rates (denormalized flags), failure patterns (denormalized flags), timeout analysis (denormalized flags), retry frequency (denormalized count)
  - `job_budgets` table: Token usage trends
- **Cached data sources (DynamoDB, precomputed):**
  - Cached `cold_start_metrics` DynamoDB table: Lambda cold start data (updated every 5 minutes by scheduled Lambda)
  - Cached `health_indicators` DynamoDB table: Daily cost, API rate limits, Lambda concurrency (updated every minute by scheduled Lambda)
  - **Note:** CloudWatch Logs Insights queries are multi-second to tens of seconds and can be throttled, so they cannot be in the <3s page-load hot path - **Solution:** Precompute and cache in DynamoDB tables
- **Denormalization strategy:** To avoid heavy `decision_events_by_job` scans at scale, denormalize key timestamps, counts, and flags into `generation_metrics` summary at job completion:
  - Stage timestamps: `t_manager_goal_formulated_ms`, `t_worker_plan_created_ms`, `t_evaluator_requested_ms`, `t_evaluator_completed_ms`, `t_manager_iteration_selected_ms`
  - Sub-worker counts: `sub_workers_spawned_count`, `sub_workers_completed_count`
  - Tool metrics: `tool_calls_total_latency_ms`, `cost_by_provider: {dynamodb_usd, web_search_usd, llm_api_usd}`
  - Success/failure flags: `had_manager_success`, `had_worker_success`, `had_failure`, `had_timeout`, `retry_count`
  - **Result:** Dashboard can query `generation_metrics` summary records directly (GSI2 by date_partition) without scanning event tables

### Data Models

**API Response Schema:**
```json
{
  "date_range": {
    "start_date": "YYYY-MM-DD",
    "end_date": "YYYY-MM-DD"
  },
  "total_jobs_in_range": number,
  "timing_analysis": {
    "end_to_end_percentiles": {
      "p50": number, // seconds
      "p90": number, // seconds
      "p99": number, // seconds
      "sample_size": number, // included jobs (completed_at >= created_at and both exist)
      "excluded_count": number // excluded jobs (missing timestamps, non-monotonic: completed_at < created_at)
    },
    "stage_breakdown": [
      {
        "stage": string, // "manager_goal_formulation" | "worker_execution_planning" | "sub_worker_execution" | "tool_calls" | "evaluator_wait" | "manager_evaluation"
        "avg_time_ms": number, // null if stage missing (excluded from avg) - **Chart displays this value**
        "p50_ms": number, // null if stage missing (excluded from percentile) - **Shown in tooltip or table**
        "p90_ms": number, // null if stage missing (excluded from percentile) - **Shown in tooltip or table**
        "p99_ms": number, // null if stage missing (excluded from percentile) - **Shown in tooltip or table**
        "sample_size": number // jobs with this stage (non-null durations)
      }
    ],
    "note": string, // "Avg stage time (may overlap)" - stage durations are independent measurements
    "lambda_cold_start": {
      "manager_lambda": {
        "cold_start_ms": number, // average first request
        "warm_ms": number // average subsequent requests
      },
      "worker_lambda": {
        "cold_start_ms": number,
        "warm_ms": number
      },
      "sub_worker_lambda": {
        "cold_start_ms": number,
        "warm_ms": number
      },
      "evaluator_lambda": {
        "cold_start_ms": number,
        "warm_ms": number
      },
      "last_computed_at": string // ISO timestamp of when cold start data was computed
    }
  },
  "cost_analysis": {
    "token_usage_trends": [
      {
        "date": "YYYY-MM-DD",
        "prompt_tokens": number,
        "completion_tokens": number,
        "total_tokens": number
```

**Stage Breakdown Calculation (Explicit Rules, Using Denormalized Fields):**
- Manager goal formulation: `t_manager_goal_formulated_ms` (offset from job `created_at` in milliseconds) - **Rule:** If field missing, stage duration = null and exclude from percentile denominator
- Worker execution planning: `t_worker_plan_created_ms - t_manager_goal_formulated_ms` (difference between offsets) - **Rule:** If field missing, stage duration = null and exclude from percentile denominator
- Sub-worker execution: `sub_worker_max_duration_ms` (denormalized max duration across all invocations) - **Rule:** Use denormalized `sub_worker_max_duration_ms` field (computed at job completion) - **Rule:** Use `sub_workers_spawned_count` to determine if sub-workers ran - **Rule:** If no sub-workers spawned, stage duration = null and exclude from percentile denominator
- Tool calls: `tool_calls_total_latency_ms` (denormalized sum of all tool call latencies) - **Rule:** Tool calls stage = sum of all tool call latencies for the job, independent of overlap with other stages - **Rule:** Use denormalized `tool_calls_total_latency_ms` field in `generation_metrics` summary - **Rule:** If no tool calls, stage duration = 0 (not null)
- Evaluator wait: `t_evaluator_completed_ms - t_evaluator_requested_ms` (difference between offsets) - **Rule:** If field missing, stage duration = null and exclude from percentile denominator
- Manager evaluation: `t_manager_iteration_selected_ms - t_evaluator_completed_ms` (difference between offsets) - **Rule:** If field missing, stage duration = null and exclude from percentile denominator
- **Note:** Stage durations are independent measurements and may overlap due to parallelism - **Label explicitly:** "Avg stage time (may overlap)" - **Visualization:** Grouped bar chart (not stacked) displaying `avg_time_ms` per stage - **Percentiles:** p50/p90/p99 shown in tooltip (or small table below chart)

**Lambda Cold Start Detection:**
- Query CloudWatch Logs Insights for Lambda function logs
- Extract `REPORT RequestId` lines with `Duration` and `Billed Duration`
- Identify first request per Lambda function (cold start) vs. subsequent requests (warm)
- Average cold start latency and warm latency per Lambda function

**Cost Guardrail Effectiveness:**
- Trigger rate: `count(jobs where cost_guardrail_triggered = true) / total_jobs`
- Acceptance rate when triggered: `count(jobs where cost_guardrail_triggered = true AND user_accepted = true) / count(jobs where cost_guardrail_triggered = true)`
- Acceptance rate normal: `count(jobs where cost_guardrail_triggered = false AND user_accepted = true) / count(jobs where cost_guardrail_triggered = false)`
- Acceptance rate difference: `acceptance_rate_when_triggered - acceptance_rate_normal`

**Success Rate Calculation (Positive Signals, Using Denormalized Fields):**
- Manager: `count(jobs where had_manager_success = true) / count(jobs where had_manager_success is not null)` - **Denormalized field:** `had_manager_success` boolean flag in generation_metrics summary - **Prefer positive signals:** Presence of `manager_iteration_selected` event, not absence of `manager_failed` - **Rule:** If field is null, exclude from denominator (component never ran)
- Worker: `count(jobs where had_worker_success = true) / count(jobs where had_worker_success is not null)` - **Denormalized field:** `had_worker_success` boolean flag in generation_metrics summary - **Rule:** If field is null, exclude from denominator (component never ran)
- Sub-workers: `count(jobs where sub_workers_completed_count == sub_workers_spawned_count) / count(jobs where sub_workers_spawned_count > 0)` - **Denormalized fields:** `sub_workers_spawned_count`, `sub_workers_completed_count` in generation_metrics summary - **Rule:** Compare counts: if spawned_count == completed_count, success; if completed_count < spawned_count, failure - **Rule:** If no sub-workers spawned, exclude from denominator
- Evaluator: `count(evaluator requests where evaluator_status = "completed") / total_evaluator_requests` - **Denormalized field:** `evaluator_status` in generation_metrics summary - **Already using positive signal:** `evaluator_status="completed"` is correct

### Technical Constraints

**Data Aggregation (Single Endpoint with Cached Data):**
- **Primary data sources (DynamoDB):**
  - Query `jobs` table for end-to-end timing (date range filter on `created_at`) - **Data hygiene:** Only include jobs where `completed_at >= created_at` and both exist (timestamps in UTC ISO-8601)
  - Query `generation_metrics` summary records (GSI2 by date_partition) for stage breakdown, cost, efficiency, success rates, failure patterns, timeout analysis, retry frequency - **Denormalized fields:** Use `t_manager_goal_formulated_ms`, `t_worker_plan_created_ms`, `sub_workers_spawned_count`, `sub_workers_completed_count`, `t_evaluator_requested_ms`, `t_evaluator_completed_ms`, `t_manager_iteration_selected_ms`, `tool_calls_total_latency_ms`, `cost_by_provider`, `had_manager_success`, `had_worker_success`, `had_failure`, `had_timeout`, `retry_count` - **Avoids heavy event scans:** No need to query `decision_events_by_job` table for aggregations
  - Query `job_budgets` table for token usage trends (aggregate by `created_at` date)
- **Cached data sources (DynamoDB, precomputed):**
  - Query cached `cold_start_metrics` DynamoDB table (updated every 5 minutes by scheduled Lambda) - **NOT in hot path:** CloudWatch Logs Insights queries are multi-second to tens of seconds, so precompute and cache
  - Query cached `health_indicators` DynamoDB table (updated every minute by scheduled Lambda) - **NOT in hot path:** CloudWatch GetMetricData has limits and cost considerations, so precompute and cache
- **Single endpoint:** `/api/v1/dashboard/performance` returns all metrics inline (Tier A + Tier B cached data)
- **Aggregate in-memory after queries (target <2s response time)**

**Chart Library:**
- Use Recharts library (lazy-loaded via dynamic import)
- All charts must be responsive (adjust to container width)
- Charts must handle empty data gracefully (display "No data available" message)

**Statistical Calculations:**
- Percentiles: Use numpy.percentile or equivalent (p50, p90, p99)
- Box plot: Calculate min, Q1, median, Q3, max, outliers (IQR method)
- Success rates: Count successful / total * 100
- Timeout rates: Count timeouts / total * 100

**Mobile Responsiveness:**
- Dashboard must work on 360px width minimum
- Tables must be scrollable on mobile
- Charts must adjust to container width
- Progress bars must be readable on mobile

**Real-Time Updates:**
- Health indicators poll CloudWatch metrics every 30-60 seconds
- System status can use WebSocket for real-time updates (optional enhancement)
- Daily cost progress bar updates automatically
