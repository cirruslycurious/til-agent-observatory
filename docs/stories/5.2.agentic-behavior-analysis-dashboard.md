# Story 5.2: Agentic Behavior Analysis Dashboard

## Status

Draft

## Story

**As an** AI developer  
**I want** detailed analysis of tool usage and sub-worker patterns  
**So that** I can understand autonomous decision-making

## Acceptance Criteria

**Dashboard Page:**
1. Dashboard page accessible at `/dashboard/behavior` route (public, same security as Story 5.1)
2. Page loads in <3 seconds (including data fetch)
3. Mobile responsive (works on 360px width minimum)
4. Uses Recharts library (lazy-loaded) for all chart visualizations
5. All metrics fetched from `/api/v1/dashboard/behavior` endpoint (single API call for all metrics)

**Tool Usage Heatmap:**
6. 2D heatmap visualization showing tool usage frequency by vendor-role combination
7. X-axis: Tool types (snake_case enums: `dynamodb_lookup`, `web_search`, etc.) - **Extensible enum** (from Story 3.3) - **UI displays friendly labels** (e.g., "DynamoDB Lookup", "Web Search")
8. Y-axis: Vendor-Role combinations (snake_case keys: `openai_worker`, `anthropic_worker`, `openai_manager`, `anthropic_manager`) - **UI displays friendly labels** (e.g., "OpenAI Worker", "Anthropic Manager")
9. Color intensity: Frequency of tool usage (darker = more frequent)
10. Hover tooltip: Exact count, percentage of total tool calls, and **total tool calls count** (denominator for percentages)
11. Chart uses Recharts or custom heatmap component (lazy-loaded)
12. **Stable source for vendor + actor:** `tool_called` event must include explicit fields: `actor_role` (manager|worker|sub_worker|evaluator) and `vendor` (openai|anthropic) - **Add to Story 3.3 event shape requirement**
13. Data aggregated from `decision_events_by_job` table (filter `event_type = "tool_called"`) - **Use GSI_TOOL_CALLS for efficient queries** (PK = event_type#YYYY-MM-DD, SK = timestamp#job_id) OR pre-aggregated rollup table (tool_usage_daily or daily_metrics extension)

**Sub-Worker Orchestration Treemap:**
13. Treemap visualization showing sub-worker orchestration patterns (hierarchical: Worker → pattern → sub-worker type combos)
14. Root: Worker
15. Level 1: Pattern (or execution_mode: parallel | sequential) - **snake_case enum** (UI displays friendly labels)
16. Level 2: Sub-worker type combos (e.g., "cfp+evidence", "draft+red_team") - **snake_case enum** (UI displays friendly labels like "CFP + Evidence")
17. Size: Frequency of pattern (larger = more common)
18. Color: Submit-worthy rate (accept + would_submit_with_edits) - green = high, red = low
19. Chart uses Recharts Treemap component (lazy-loaded) - **Recharts supports Treemap well, reduces implementation risk vs. custom sunburst**
20. Click: Drill down to example job IDs (navigate to job detail page)
21. Data aggregated from `generation_metrics` table (summary records, `sub_worker_types_spawned` array and `sub_worker_patterns` field)

**Tool Call Sequence Sankey Diagram:**
22. Sankey diagram showing flow: Worker decision → Tools called → Sub-workers spawned → Outcome
23. Flow visualization:
    - Left: Worker decision (strategy_decision event) - **Top K decisions only** (e.g., top 5, everything else → "Other")
    - Middle: Tools called (tool_called events) - **Top N tools only** (e.g., top 8, everything else → "Other")
    - Right: Sub-workers spawned (sub_worker_spawned events) - **Top M patterns only** (e.g., top 8, everything else → "Other")
    - Far right: Outcome (human_verdict: accept, would_submit_with_edits, would_not_submit, reject) - **snake_case enum** (UI displays friendly labels)
24. Thickness: Frequency of path (thicker = more common)
25. Color: Success rate (green = accepted/would_submit_with_edits, red = rejected/would_not_submit)
26. Interactive: Click path to see example job IDs (up to X per link, e.g., 10 job IDs max)
27. Chart uses Recharts Sankey component (lazy-loaded) - **Recharts Sankey is limited but acceptable for MVP; constrain graph size to keep readable**
28. **Graph constraints:** Only include top K worker decisions (top 5), top N tools (top 8), top M sub-worker patterns (top 8), everything else rolled into "Other" - **Prevents unreadable graphs**
29. Data aggregated from `decision_events_by_job` table (filter by `event_type IN ("strategy_decision", "tool_called", "sub_worker_spawned")`) and `generation_metrics` table (outcome) - **Use GSI for efficient queries or pre-aggregated rollup table**

**Task Decomposition Analysis:**
29. Table showing orchestration patterns with metrics:
    - Pattern name (e.g., "Parallel CFP + Evidence", "Sequential CFP → Draft → Red Team") - **snake_case enum in storage** (UI displays friendly labels)
    - Frequency count (number of jobs using this pattern)
    - Submit-worthy rate (percentage of jobs with this pattern that were accepted or would_submit_with_edits)
    - Avg tokens used (average tokens for jobs with this pattern)
    - Avg time saved vs. sequential (seconds saved by parallel execution, if applicable) - **Computation defined:**
      - If parallel: `parallel_wall_time = max(sub_worker_time_ms[])`
      - Sequential baseline: `sum(sub_worker_time_ms[])`
      - `time_saved = baseline - parallel_wall_time` (clamp at >=0)
      - If sequential: `time_saved = 0`
    - Efficiency score: `avg_tokens_used / avg_time_seconds` (lower is better) - **Present both tokens and time separately, efficiency is derived metric**
30. Sortable columns: Frequency, Submit-worthy rate, Efficiency (tokens/time ratio)
31. Responsive table (scrollable on mobile)
32. Data aggregated from `generation_metrics` table (summary records, `sub_worker_patterns` field and `sub_worker_time_ms` field)

**Autonomous Decision Quality Scores:**
33. Table showing manual expert review scores (1-5) for sample decisions:
    - Tool selection appropriateness (1-5 scale)
    - Sub-worker spawn timing (1-5 scale)
    - Strategy adaptation on retries (1-5 scale)
    - Cost-consciousness (1-5 scale)
34. Aggregate scores by vendor (OpenAI vs. Anthropic) for each dimension - **snake_case enum** (openai, anthropic)
35. Sample size (N) displayed for each score
36. **Optionality consistent:** Return `decision_quality_scores_available: boolean` and `rows: []` (stable object structure, not null) - **If `available = false`, UI displays "Not yet available" message**
37. **For MVP:** Return `decision_quality_scores_available: false` - **Later add manual_reviews table and flip the flag**

**Error Handling:**
38. If API returns no data (empty result): Display "No data available" message with helpful text
39. If API returns error: Display error message with retry button
40. Loading state: Show skeleton loaders for all charts and tables while data is fetching

**Performance:**
41. All charts lazy-loaded (dynamic import of Recharts/custom components)
42. API response cached client-side for 5 minutes (prevent excessive API calls)
43. Metrics refresh button available (manual refresh, bypasses cache)

## Dev Notes

### Previous Story Insights

From Story 3.3 (Tool Usage Logging):
- Tool calls logged to `decision_events_by_job` table (canonical timeline source)
- Event type: `tool_called`
- Tool names: Extensible enum (dynamodb_lookup, web_search, ...)
- Tool call includes: `tool_name`, `tool_invocation_id`, `params_summary`, `results_summary`, `cost_usd`, `tokens_used`, `success_status`
- Actor field: `manager`, `worker`, `sub_worker`, `evaluator`

From Story 2.3 (Sub-Worker Spawning Coordination):
- Sub-worker spawns logged to `decision_events_by_job` table
- Event type: `sub_worker_spawned`
- Sub-worker types: `cfp_extractor`, `evidence_researcher`, `draft_generator`, `red_team_reviewer`
- Sub-worker patterns stored in `generation_metrics` table (`sub_worker_patterns` field)
- Parallel vs. sequential execution tracked in `generation_metrics` table (`parallel_executions` field)

From Story 2.2 (Worker Agent Autonomous Execution):
- Strategy decisions logged to `decision_events_by_job` table
- Event type: `strategy_decision`
- Strategy decision includes: `sub_workers_to_spawn`, `tools_to_use`, `reasoning`

From Story 6.2 (DynamoDB Generation Metrics Storage):
- `generation_metrics` table stores summary records with `sub_worker_types_spawned` array and `sub_worker_patterns` field
- `human_verdict` field stores outcome (accept, would_submit_with_edits, would_not_submit, reject)
- `total_tokens` and `total_time_seconds` fields for efficiency metrics

**Key Insight:** Behavior analysis queries `decision_events_by_job` table (canonical timeline) for tool calls and sub-worker spawns, and `generation_metrics` table (summary records) for patterns and outcomes. Charts visualize autonomous decision-making patterns.

### API Specifications

**Behavior Analysis Endpoint:**
- **Endpoint:** `GET /api/v1/dashboard/behavior`
- **Authentication:** Simple read token (dashboard token from env var) OR feature flag - **Same security as Story 5.1**
- **Query Parameters:**
  - `date_from`: YYYY-MM-DD (optional, default: 30 days ago) - **Dashboard range defaults to last 30 days**
  - `date_to`: YYYY-MM-DD (optional, default: today)
  - `vendor`: openai | anthropic (optional filter, snake_case enum)
  - `conference`: black_hat | reinvent | kubecon (optional filter, snake_case enum)
- **Response:** JSON object with all behavior analysis metrics (see Data Models section) - **Includes:** `generated_at` (ISO timestamp), `range: {start_date, end_date}` (date range used for aggregation, defaults to last 30 days)
- **Performance:** Response time <3 seconds (aggregation queries optimized using **GSI_TOOL_CALLS** on decision_events_by_job table OR pre-aggregated rollup table) - **Cheap aggregation path: GSI by event_type#date or daily_metrics extensions**
- **Caching:** Client-side caching for 5 minutes (prevent excessive API calls)
- **Data range:** Uses last 30 days by default (or all time if <30 days of data)

### Technical Constraints

**Performance:**
- Dashboard page load time: <3 seconds (including data fetch)
- API response time: <3 seconds (aggregation queries optimized using GSI2 and decision_events_by_job table)
- Client-side caching: 5 minutes (prevent excessive API calls)

**Data Aggregation:**
- Use `decision_events_by_job` table (canonical timeline) for tool calls and sub-worker spawns
- Use `generation_metrics` table (summary records, GSI2) for patterns and outcomes
- Aggregate only summary records (record_type = "summary") from `generation_metrics` table

**Chart Library:**
- Use Recharts library (lazy-loaded via dynamic import) - **Recharts supports Treemap well, Sankey is limited but acceptable for MVP**
- All charts must be responsive (adjust to container width)
- Charts must handle empty data gracefully (display "No data available" message)
- **Treemap:** Recharts Treemap component (replaces sunburst, reduces implementation risk)
- **Sankey:** Recharts Sankey component (limited but acceptable for MVP; constrain graph size to keep readable)

**Mobile Responsiveness:**
- Dashboard must work on 360px width minimum
- Tables must be scrollable on mobile
- Charts must adjust to container width
