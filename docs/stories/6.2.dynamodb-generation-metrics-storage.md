## Status

Approved

## Story

**As the** system

**So that** dashboard can query effectively

## Acceptance Criteria

**Table: generation_metrics**

**Schema:**
1. Table created with partition key: job_id (String, UUID) - **Canonical ID name everywhere (avoid "generation_id == job_id" confusion)**
2. Sort key: record_type#timestamp (String, e.g., "summary#2026-01-12T10:31:27Z")
3. **GSI1 (Time-Series):** date_partition (String, YYYY-MM-DD) + timestamp (String, ISO datetime, pure time ordering) for time-series queries
4. **GSI2 (Summary Aggregation):** date_partition (String, YYYY-MM-DD) + record_type#timestamp (String, e.g., "summary#2026-01-12T10:31:27Z") for nightly aggregation (summary records only)
5. **Timestamp attribute:** timestamp (String, ISO 8601 with Z, first-class attribute, always present) - Used for GSI sort key
6. Billing mode: On-demand (metrics are variable size, unpredictable access patterns)
7. Point-in-time recovery: Enabled (for audit trail and data recovery)

**Attributes:**
6. Request Context: job_id (String, UUID, PK), user_session_id, conference, topic, timestamp (String, ISO 8601 with Z, first-class attribute), date_partition (String, YYYY-MM-DD)
7. Vendor Assignment: manager_vendor, manager_model, worker_vendor, worker_model, evaluator_model
8. Iteration Control: total_iterations (1-5), selected_iteration (0-4), creativity_progression[] (array of numbers, keep small), iteration_details[] (array of iteration objects, keep summary only - full details in decision_events)
9. User Feedback: user_accepted (boolean), user_intent (string, validated), user_feedback_time, user_comment (max 500 chars)
10. Sub-Worker Data: sub_workers_spawned[] (array of sub-worker types, keep small), sub_worker_patterns (string), parallel_executions (number), sub_worker_time_ms (number)
11. Tool Usage: tool_calls_made[] (array of tool names, keep small), tool_sequences[] (array of tool call sequences, keep summary only - full sequences in decision_events), tool_effectiveness (number 0-1, optional), cost_guardrail_triggered (boolean), minimal_tool_mode_activated (boolean)
12. Manager Data: manager_feedback[] (array of feedback objects, keep summary only - full feedback in decision_events), manager_evaluation_time_ms (number)
13. Evaluator Data: evaluator_result {top_3, confidence_scores, reasons}, evaluator_timeout (boolean), evaluator_response_time_ms (number), evaluator_agreement (boolean, optional)
14. Performance: total_tokens (number), tokens_by_component (object with numbers), total_cost_usd (number), total_time_seconds (number)
15. Artifacts: scratch_artifacts[] (array of artifact_id references, not full artifacts), evidence_quality (string, optional), final_output (string, summary max 500 chars), final_output_s3_ref (string, S3 key, optional)
16. **Item size management:** Summary record must stay <350KB (keep arrays small, store references not full data, use S3 for large blobs)

**Key Constraints:**
17. Conference field: CLOSED SET ["black_hat", "reinvent", "kubecon"] - validate before write (central enum definition shared across Python + TS)
18. Evaluator top_3: CLOSED SET (same 3 conferences: black_hat, reinvent, kubecon) - validate before write (central enum definition)
19. User intent: CLOSED SET ["would_submit_with_edits", "would_not_submit"] - validate before write (central enum definition, may expand in future)
20. Total iterations: 1-5 hard cap - validate before write
21. All closed set fields validated before write (raise ValidationError if invalid)
22. **Central enum definitions:** Store closed set values in shared enum files (Python: enum.Enum, TypeScript: const enum) to prevent drift

**Record Types:**
21. record_type = "summary": Final job summary (written once per job on completion)
22. record_type = "iteration": Per-iteration snapshot (written once per iteration, 0-4 iterations)
23. record_type = "event": Significant events (optional, for detailed timeline reconstruction)
24. Primary record: record_type = "summary" (contains all aggregated metrics for dashboard queries)

**Dashboard Query Optimization:**
25. Precomputed daily aggregates in separate table: daily_metrics
26. Lambda runs nightly to aggregate metrics by date_partition (yesterday's date)
27. **Nightly aggregation uses GSI2 (Summary Aggregation):** Query GSI2 by date_partition, filter to summary records only (KeyCondition: date_partition = yesterday AND begins_with(record_type#timestamp, "summary#")) - prevents reading iteration/event records
28. Dashboard reads from daily_metrics for historical data (fast, precomputed)
29. Dashboard reads from generation_metrics for today's data (real-time, GSI1 query by date_partition, sort by timestamp)
30. Query pattern: GSI1 query by date_partition for time-series data (last 30 days), sort by timestamp (pure time ordering)

**Table: daily_metrics**
31. Table created with partition key: metric_date (String, YYYY-MM-DD)
32. Sort key: metric_type#schema_version (String, e.g., "acceptance_by_vendor#v1", "tool_usage#v1") - **Includes schema versioning for metric evolution**
33. Attributes: precomputed_data (JSON, chart-ready), schema_version (String, e.g., "v1"), updated_at (ISO timestamp)
34. No GSIs (not needed for daily aggregation queries)
35. Billing mode: On-demand (low volume, daily updates)
36. Point-in-time recovery: Enabled (for audit trail)
37. **Schema versioning:** When metric structure changes, increment schema_version (v1 → v2), update SK to metric_type#v2, keep old version for backward compatibility

**Nightly Aggregation Lambda:**
38. Scheduled Lambda function runs daily at 00:00 UTC (or configurable time)
39. **Query strategy (GSI2 for summaries only):** Query GSI2 by date_partition = yesterday, KeyCondition: `date_partition = :yesterday AND begins_with(record_type#timestamp, :summary_prefix)` where summary_prefix = "summary#" - **Only reads summary records, not iteration/event records (cost-efficient)**
40. Aggregates metrics from generation_metrics table for previous day (date_partition = yesterday, summary records only)
41. Computes precomputed slices:
    - acceptance_by_vendor (acceptance rate by manager_vendor, worker_vendor)
    - tool_usage_by_vendor_role (tool call frequency by vendor and role)
    - guardrail_rate_by_vendor_role (cost guardrail trigger rate)
    - p50_p90_latency_by_conference_topic (performance percentiles)
    - evaluator_accuracy (top-1, top-3 match rates) - **Truth label:** Match against "actual conference requested" (from request_context.conference)
    - sub_worker_patterns (orchestration pattern frequency)
42. Writes precomputed_data to daily_metrics table (one record per metric_type#schema_version per day, e.g., "acceptance_by_vendor#v1")
43. Handles errors gracefully (log errors, don't fail silently, retry on transient failures)

### API Specifications

**Dashboard Metrics Query Endpoint:**
- **Endpoint:** `GET /api/v1/dashboard/metrics?date_from={YYYY-MM-DD}&date_to={YYYY-MM-DD}&metric_type={type}[&vendor={vendor}][&conference={conference}]`
- **Authentication:** None (public dashboard endpoint, aggregated data only)
- **Query Parameters:**
  - `date_from`: YYYY-MM-DD (optional, default: 30 days ago)
  - `date_to`: YYYY-MM-DD (optional, default: today)
  - `metric_type`: String (optional, filter by metric type)
  - `vendor`: openai | anthropic (optional filter)
  - `conference`: black_hat | reinvent | kubecon (optional filter)
- **Response:** Chart-ready JSON (merged from daily_metrics and generation_metrics)
- **Query Strategy:**
  - Historical data (date_from to yesterday): Query daily_metrics table
  - Today's data: Query generation_metrics table (GSI by date_partition)
  - Merge results and return

### Technical Constraints

**Table Design:**
- generation_metrics: PK=job_id (canonical ID name), SK=record_type#timestamp, GSI1=date_partition+timestamp (pure time ordering), GSI2=date_partition+record_type#timestamp (summary aggregation)
- daily_metrics: PK=metric_date, SK=metric_type#schema_version (includes schema versioning)
- Billing mode: On-demand (variable size, unpredictable access patterns)
- Point-in-time recovery: Enabled (for audit trail and data recovery)

**Validation:**
- Closed set fields validated before write: conference, evaluator top_3, user_intent, total_iterations
- **Central enum definitions:** Store closed set values in shared enum files (Python: enum.Enum, TypeScript: const enum) to prevent drift
- If validation fails: Raise ValidationError, do NOT write metrics
- Validation functions: validate_conference (uses shared enum), validate_evaluator_top_3 (uses shared enum), validate_user_intent (uses shared enum), validate_total_iterations

**Query Optimization:**
- Historical data: Query daily_metrics table (precomputed, fast)
- Today's data: Query generation_metrics table (GSI1 by date_partition, sort by timestamp, real-time)
- Merge strategy: Dashboard endpoint merges both sources for complete picture
- **Nightly aggregation:** Uses GSI2 (Summary Aggregation) to query only summary records (cost-efficient, prevents reading iteration/event records)

**Nightly Aggregation:**
- Runs daily at 00:00 UTC (configurable)
- **Query strategy (GSI2 for summaries only):** Query GSI2 by date_partition = yesterday, KeyCondition: `date_partition = :yesterday AND begins_with(record_type#timestamp, :summary_prefix)` - **Only reads summary records, not iteration/event records (cost-efficient)**
- Aggregates previous day's metrics (date_partition = yesterday, summary records only)
- Computes precomputed slices for common dashboard queries
- Writes to daily_metrics with schema versioning (metric_type#schema_version, e.g., "acceptance_by_vendor#v1")
- **evaluator_accuracy truth label:** Match against request_context.conference (actual conference requested)
- Handles errors gracefully (log errors, retry on transient failures)

**Record Types:**
- "summary": Final job summary (written once per job on completion, must stay <350KB)
- "iteration": Per-iteration snapshot (written once per iteration, 0-4 iterations)
- "event": Significant events (optional, for detailed timeline reconstruction)

**Item Size Management:**
- Summary record must stay <350KB (DynamoDB limit: 400KB)
- Keep arrays small: tool_calls_made[], sub_workers_spawned[], iteration_details[] (store references, not full data)
- Store references: scratch_artifacts[] (artifact_id references), tool_sequences[] (summary only, full sequences in decision_events)
- Use S3 for large blobs: final_output_s3_ref if final_output >500 chars
