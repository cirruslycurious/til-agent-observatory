# Story 1.2: Dual-Layer Workflow Visualization

## Status

Approved

## Story

**As an** AI developer  
**I want to** view agent decision-making in both Simple and Deep modes  
**So that** I can choose my level of detail engagement

## Acceptance Criteria

**Simple View:**
1. Timeline shows major steps: Manager → Worker → Sub-workers → Synthesis → Evaluator (5 stages)
2. Artifact cards display for each sub-worker with collapsed preview
3. Key decision summaries shown (e.g., "Worker spawned CFP Extractor to analyze conference rules")
4. Visual progress indicators update in real-time
5. Parallel execution visualized via sub-worker lanes/cards shown concurrently (not sequentially)
6. Tab labeled "Workflow (Simple)"
7. Default view on first load
8. On screens < 768px, default to Workflow (Simple); Deep view remains accessible

**Deep View:**
8. Complete tool call details with parameters and results summary
9. Raw source snippets (not full payloads, max 200 chars per source)
10. Token usage and timing per step
11. Evaluator summary + reasoning displayed; raw payload accessible via link (not embedded)
12. Artifact dependency graphs (visual tree showing which artifacts feed which)
13. Evidence chains with clickable pointers to sources
14. Tab labeled "Workflow (Deep)"
15. Switch between Simple/Deep without losing place

**Both Views:**
16. Real-time updates via WebSocket (fallback to polling if WS fails)
17. Vendor assignments revealed after generation starts (not before)
18. Clearly labeled which vendor is Manager, which is Worker
19. Logs preserved after generation completes (can review)
20. Header shows job_id, status, connection mode (WS/polling), and last update timestamp
21. Switch between Simple/Deep preserves scroll position per tab and expanded/collapsed state per EventCard (Deep view)

## Dev Notes

### Previous Story Insights

**From Story 1.1:**
- LandingPage navigates to `/generate/:jobId` after successful API call
- Token stored in sessionStorage with key: `cab:job_token:<jobId>`
- GenerationPage should check for token on mount and show recovery UI if missing
- Use React Router `useParams` to extract `jobId` from URL

**Backend/API Observability Requirements:**
To make Deep View possible without hacks, backend MUST emit these fields consistently:
- `event_id` (or stable synthetic ID) - Required for deduplication
- `seq` (or monotonic ordering per job) - Required for sorting
- `stage` or `phase` mapping - Required for Timeline stage assignment (not guessing)
- `artifact.dependencies[]` with IDs that exist - Required for dependency graphs
- `sources[]` with `{type, url, snippet}` already truncated server-side (defense-in-depth, max 200 chars)
- `timing_ms` - Required for timing display
- `token_usage` - Required for token usage display

**Note:** If any of these are "optional", the UI becomes messy. Backend must guarantee these fields are present.

### Data Models

```typescript

  job_id: string; // UUID

    tool_params?: Record<string, unknown>;

      input_tokens: number;
      output_tokens: number;
      total_tokens: number;

    sources?: Array<{
      type: string;
      url?: string;
      snippet: string; // Max 200 chars
    }>;
    artifact_id?: string;
    artifact_type?: string;
    dependencies?: string[]; // Array of artifact_ids this depends on
  };

}
```

### API Specifications

**WebSocket Connection:**
- URL: `wss://api.example.com/ws?job_id={jobId}` (token NOT in URL)
- Auth: Send auth message frame after connection: `{ type: 'auth', job_id: string, token: string }`
- Auth timeout: 3 seconds (fallback to polling if auth fails)
- Messages: `decision_event`, `progress`, `completed`, `failed`, `auth_success`, `auth_failed`

**Polling Fallback:**
- Endpoint: `GET /api/v1/status/{job_id}?token={token}`
- Interval: 2 seconds when polling-only
- Heartbeat: 20 seconds when WebSocket connected

**Workflow Events API:**
- Endpoint: `GET /api/v1/workflow/{job_id}?token={token}`
- Returns: Array of decision events (chronological)
- Use for initial load or recovery

### WebSocket Integration

**Connection Flow:**
1. Connect to `wss://api.example.com/ws?job_id={jobId}` (no token in URL)
2. Send auth message frame: `{ type: 'auth', job_id, token }`
3. Wait for `auth_success` or `auth_failed` (3 second timeout)
4. If auth fails, fallback to polling
5. Subscribe to `decision_event`, `progress`, `completed`, `failed` messages

**Event Handling:**
- `decision_event`: Add to jobStore using `addWorkflowEvent`
- `progress`: Update progress indicators
- `completed`: Update jobStatus to 'completed', show Results tab
- `failed`: Update jobStatus to 'failed', show error message

**Polling Fallback:**
- Use `usePolling` hook when WebSocket unavailable
- Poll `/api/v1/status/{job_id}` every 2 seconds
- Merge events from status response into jobStore

[Source: docs/frontend-architecture.md#WebSocket-Client, docs/frontend-architecture.md#WebSocket-+-Polling-Coordination]

   - Test SimpleView renders with timeline and artifact cards
   - Test DeepView renders with all events
   - Test Timeline displays stages correctly
   - Test EventCard displays event details
   - Test ArtifactCard displays artifact metadata

2. **View Switching:**
   - Test switching between Simple and Deep views
   - Test scroll position preservation per tab (scrollPositions in uiStore)
   - Test expanded/collapsed state preservation per EventCard (Deep view)
   - Test Results tab visibility (only when completed)
   - Test mobile default to Simple view (< 768px)

3. **Event Handling:**
   - Test event deduplication (same event_id not added twice)
   - Test event sorting (chronological order)
   - Test real-time updates (WebSocket messages)
   - Test polling fallback (when WebSocket fails)

4. **Vendor Assignment & Job Header:**
   - Test vendor assignment hidden until first event
   - Test vendor assignment display (Manager/Worker labels)
   - Test job header displays: job_id, status, connection mode, last update timestamp

5. **Progress Indicators:**
   - Test progress bar updates with progress messages
   - Test stage indicators update correctly

6. **Accessibility:**
   - Test keyboard navigation (tabs, cards)
   - Test screen reader compatibility
   - Test ARIA attributes
