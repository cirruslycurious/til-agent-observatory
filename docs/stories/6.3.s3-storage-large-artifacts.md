# Story 6.3: S3 Storage for Large Artifacts

## Status

Draft

## Story

**As the** system  
**I need** S3 storage for artifacts exceeding DynamoDB limits  
**So that** large tool results and artifacts don't fail

## Acceptance Criteria

**S3 Bucket: scratch-artifacts-{environment}**

**Bucket Configuration:**
1. Bucket created with name: `scratch-artifacts-{environment}` (e.g., `your-artifacts-bucket`, `scratch-artifacts-prod`)
2. Versioning: Enabled (protects against accidental overwrites, buggy writers, or future code changes - cheap insurance even though application contract is "immutable")
3. Encryption: Server-side encryption with AWS managed keys (SSE-S3) - **Note:** Upgrade to SSE-KMS in prod if compliance requires audit/controls
4. Public access: Block all public access (private bucket)
5. CORS: Not configured (Lambdas access directly, no browser CORS needed)
6. Lifecycle policy: Intelligent-Tiering storage class, configure to move to Archive Access after 365 days of no access; Deep Archive after N days (optional)
7. Retention: Indefinite (until manual cleanup or lifecycle policy)

**Bucket Structure:**
8. S3 key pattern: `s3://scratch-artifacts-{environment}/{job_id}/{task_id}/{artifact_version}/{object_name}`
9. **artifact_version uniqueness:** artifact_version must be unique per (job_id, task_id); writers must never reuse a version (monotonically increasing per task, e.g., v0001, v0002, v0003)
10. Object naming:
    - `full_artifact.json`: Complete artifact payload if >=350KB
    - `tool_results/{tool_call_id}.json`: Raw tool outputs if >50KB (per tool call, unique per tool_call_id to prevent overwrites)
    - `metadata.json`: Artifact envelope copy for audit (optional, for debugging)
11. Directory structure example:
    ```
    s3://scratch-artifacts-prod/
      {job_id}/
        {task_id}/
          v0001/
            full_artifact.json
            tool_results/
              {tool_call_id_1}.json
              {tool_call_id_2}.json
          v0002/
            full_artifact.json
    ```

**Upload Logic - Artifacts:**
12. If artifact size >= 350KB:
    - [ ] Upload full artifact JSON to S3: `s3://scratch-artifacts-{environment}/{job_id}/{task_id}/{artifact_version}/full_artifact.json`
    - [ ] Generate SHA-256 hash of full artifact payload using canonical JSON serialization (UTF-8, stable key order, no whitespace differences - e.g., sort_keys=True, separators=(',', ':') in Python) - **payload_sha256_raw**
    - [ ] If compressed: Generate SHA-256 hash of compressed bytes (after gzip) - **payload_sha256_stored** (optional, for debuggability)
    - [ ] Write summary (max 10KB) to DynamoDB `data` field
    - [ ] Set `overflow.s3_payload_ref` = S3 key
    - [ ] Set `overflow.payload_sha256` = SHA-256 hash of raw JSON bytes (before compression)
    - [ ] Set `overflow.payload_sha256_stored` = SHA-256 hash of compressed bytes (optional, if compressed)
    - [ ] Set `overflow.payload_size_bytes` = actual size before compression
    - [ ] Set `overflow.compressed` = true/false (if compression applied)
    - [ ] Add S3 object tags/metadata: job_id, artifact_id, created_at, writer_request_id (for orphan cleanup)
13. If artifact size < 350KB: Store full artifact in DynamoDB `data` field (no S3 upload)
14. **Atomicity definition:** "Never create a DynamoDB pointer to a missing S3 object." Implementation:
    - [ ] Upload object to S3 with deterministic key
    - [ ] Verify upload succeeded (head/get, or rely on SDK success)
    - [ ] Write DynamoDB item including s3_payload_ref
    - [ ] If DynamoDB write fails after S3 succeeded → orphaned S3 object may exist (acceptable, periodic cleanup by prefix using object tags/metadata)
15. Upload includes metadata: Content-Type: application/json, Content-Encoding: gzip (if compressed)

**Upload Logic - Tool Results:**
16. If tool results size >50KB:
    - [ ] Upload tool results JSON to S3: `s3://scratch-artifacts-{environment}/{job_id}/{task_id}/{artifact_version}/tool_results/{tool_call_id}.json` (unique per tool_call_id to prevent overwrites)
    - [ ] Generate SHA-256 hash of tool results payload using canonical JSON serialization (UTF-8, stable key order, no whitespace differences - e.g., sort_keys=True, separators=(',', ':') in Python) - raw JSON bytes, before compression if applied
    - [ ] Add S3 object tags/metadata: job_id, tool_call_id, created_at, writer_request_id (for orphan cleanup)
    - [ ] Write `results_summary` (50-200 chars, always summary) to DynamoDB `provenance.tool_calls[].results_summary`
    - [ ] Set `provenance.tool_calls[].s3_tool_results_ref` = S3 key
    - [ ] Set `provenance.tool_calls[].tool_results_hash` = SHA-256 hash (raw bytes)
    - [ ] Set `provenance.tool_calls[].tool_results_size_bytes` = actual size
16. If tool results size <=50KB:
    - [ ] Write `results_summary` (50-200 chars, always summary) to DynamoDB `provenance.tool_calls[].results_summary`
    - [ ] Write `results_inline` (full tool results payload) to DynamoDB `provenance.tool_calls[].results_inline` (no S3 upload)
18. **Atomicity definition:** "Never create a DynamoDB pointer to a missing S3 object." Implementation:
    - [ ] Upload object to S3 with deterministic key (includes tool_call_id for uniqueness)
    - [ ] Verify upload succeeded (head/get, or rely on SDK success)
    - [ ] Write DynamoDB item including s3_tool_results_ref
    - [ ] If DynamoDB write fails after S3 succeeded → orphaned S3 object may exist (acceptable, periodic cleanup by prefix using object tags/metadata)

**Lifecycle Management:**
18. Storage class: Intelligent-Tiering (objects stored in INTELLIGENT_TIERING, auto-optimization between Standard and Standard-IA)
19. Archive access: Configure Intelligent-Tiering to move to Archive Access after 365 days of no access; Deep Archive after N days (optional) - based on days since last access, not creation date
20. Retention: Indefinite (no automatic deletion, manual cleanup only)
21. Lifecycle policy applies to all objects in bucket (no prefix filters needed)
22. **Orphan cleanup:** Periodic cleanup by prefix for unreferenced S3 objects (if DynamoDB write fails after S3 upload succeeds) - S3 objects include tags/metadata enabling later cleanup (created_at, job_id, artifact_id, writer_request_id)

**Access Control:**
23. IAM permissions: Lambdas have read/write permissions to bucket via IAM roles
24. Bucket policy: Deny public access, allow only IAM roles with explicit permissions
25. Pre-signed URLs: Frontend can request pre-signed URLs via API Gateway → Lambda (required for payloads >5-10MB, optional for smaller payloads)
26. API Gateway → Lambda → S3: Dashboard Deep View fetches full artifacts via API (not direct S3 access)

**Error Handling:**
27. S3 upload failures: Log error, raise exception, do NOT write to DynamoDB (atomic operation - never create DynamoDB pointer to missing S3 object)
28. S3 download failures: Log error, return 503 Service Unavailable to API caller
29. Missing S3 object: If `s3_payload_ref` exists but object not found, log warning, return 404 Not Found
30. Hash verification: On download, verify SHA-256 hash matches `overflow.payload_sha256` (integrity check):
    - [ ] Download compressed bytes from S3
    - [ ] Decompress if Content-Encoding: gzip
    - [ ] Hash raw JSON bytes (before compression) using canonical JSON serialization
    - [ ] Compare with `overflow.payload_sha256` (raw hash stored in DynamoDB)
31. **Orphan cleanup:** Accept occasional orphaned S3 objects if DynamoDB write fails after S3 upload succeeds - periodic cleanup by prefix (not critical, acceptable inconsistency mode)

**Integration Points:**
32. Story 6.1 (DynamoDB Scratch Artifacts): Artifact writer checks size, uploads to S3 if >=350KB
33. Story 3.3 (Tool Usage Logging): Tool logger checks tool results size, uploads to S3 if >50KB
34. Story 1.2 (Workflow Visualization): Deep View fetches full artifacts from S3 via API Gateway → Lambda → S3
35. Story 2.2 (Worker Agent): Worker reads artifact summaries from DynamoDB, can fetch full artifacts from S3 if needed

## Dev Notes

### Previous Story Insights

From Story 6.1 (DynamoDB Scratch Artifacts Storage):
- Artifact size threshold: 350KB (DynamoDB item size limit: 400KB)
- Artifact versioning: Zero-padded versions (v0001, v0002) for lexicographical sorting
- S3 key pattern: `s3://scratch-artifacts/{job_id}/{task_id}/{artifact_version}/full_artifact.json`
- Overflow fields: `overflow.s3_payload_ref`, `overflow.payload_sha256`, `overflow.payload_size_bytes`

From Story 3.3 (Tool Usage Logging):
- Tool results size threshold: 50KB (hard limit for results_summary in DynamoDB)
- Tool results overflow: `provenance.tool_calls[].s3_tool_results_ref` (per-tool, not in artifact.overflow)
- Tool results summary: Deterministic rule (top N titles + relevance, 200 chars max)

From Story 2.2 (Worker Agent):
- Worker reads artifact summaries from DynamoDB (data.summary, quality_signals, provenance.sources)
- Worker can escalate to overflow if needed (logged as information_sufficiency_assessed)
- Artifact synthesis uses summaries only (hard constraint, overflow escalation logged)

**Key Insight:** S3 is used for overflow storage when DynamoDB limits are exceeded. Artifacts >=350KB go to S3, tool results >50KB go to S3. Atomic operations ensure data consistency (S3 upload must succeed before DynamoDB write).

### API Specifications

**Artifact Retrieval Endpoint:**
- **Endpoint:** `GET /api/v1/workflow/{job_id}/artifacts/{artifact_id}/full?token={job_read_token}`
- **Authentication:** job_read_token (hash verification)
- **Query Parameters:**
  - `token`: job_read_token (required, hash verified)
- **Response:** Full artifact JSON (from S3 if overflow, from DynamoDB if not)
  - Content-Type: application/json
  - Content-Encoding: gzip (if compressed)
- **Guardrails for Large Payloads:**
  - If payload_size_bytes > 5-10MB: Return 413 Payload Too Large with guidance to use presigned URL
  - If payload_size_bytes > 5-10MB and presigned URL requested: Generate presigned URL (expires in 1 hour), return 200 JSON: `{ "presigned_url": "...", "expires_in": 3600 }` (optionally support redirect via `?redirect=1` query parameter)
  - If payload_size_bytes <= 5-10MB: Download from S3, verify hash, return full artifact (streaming if needed)
- **Error Responses:**
  - 404 Not Found: Artifact not found
  - 413 Payload Too Large: Artifact exceeds 5-10MB limit (use presigned URL)
  - 500 Internal Server Error: Hash mismatch
  - 503 Service Unavailable: S3 download failure
- **Access Pattern:**
  - Read artifact from DynamoDB (get s3_payload_ref, payload_size_bytes)
  - If s3_payload_ref exists and payload_size_bytes <= 5-10MB: Download from S3, verify hash, return full artifact
  - If s3_payload_ref exists and payload_size_bytes > 5-10MB: Generate presigned URL, return redirect or JSON
  - If s3_payload_ref missing: Return artifact from DynamoDB data field

### Technical Constraints

**Size Thresholds:**
- Artifact size threshold: 350KB (DynamoDB item size limit: 400KB, leave margin for metadata)
- Tool results size threshold: 50KB (hard limit for results_summary in DynamoDB)
- Compression: gzip compression applied to reduce S3 storage costs (optional, default: True)

**Atomic Operations:**
- **Atomicity definition:** "Never create a DynamoDB pointer to a missing S3 object."
- Implementation:
  1. Upload object to S3 with deterministic key
  2. Verify upload succeeded (head/get, or rely on SDK success)
  3. Write DynamoDB item including s3_payload_ref
  4. If DynamoDB write fails after S3 succeeded → orphaned S3 object may exist (acceptable, periodic cleanup by prefix)
- If S3 upload fails, do NOT write to DynamoDB (rollback)
- If S3 download fails, return 503 Service Unavailable (do NOT return partial data)
- **Orphan cleanup:** Accept occasional orphaned S3 objects if DynamoDB write fails after S3 upload succeeds - periodic cleanup by prefix (not critical, acceptable inconsistency mode)

**Hash Verification:**
- **Hash definition:** SHA-256 hash of raw JSON bytes using canonical JSON serialization (UTF-8, stable key order, no whitespace differences - e.g., sort_keys=True, separators=(',', ':') in Python, JSON.stringify with sorted keys in TypeScript) - **payload_sha256_raw**
- **Canonical serialization:** Both Python and TypeScript writers/readers must use identical canonicalization to prevent false mismatches (UTF-8 encoding, sorted keys, no whitespace)
- **Optional hash:** SHA-256 hash of compressed bytes (after gzip) - **payload_sha256_stored** (optional, for debuggability)
- Hash stored in DynamoDB (`overflow.payload_sha256` = raw hash, `overflow.payload_sha256_stored` = stored hash if compressed, `provenance.tool_calls[].tool_results_hash` = raw hash)
- Hash verified on download (integrity check):
  - Download compressed bytes from S3
  - Decompress if Content-Encoding: gzip
  - Hash raw JSON bytes using canonical JSON serialization (before compression)
  - Compare with `overflow.payload_sha256` (raw hash stored in DynamoDB)
- If hash mismatch, return 500 Internal Server Error

**Lifecycle Management:**
- Storage class: Intelligent-Tiering (objects stored in INTELLIGENT_TIERING, auto-optimization between Standard and Standard-IA)
- Archive access: Configure Intelligent-Tiering to move to Archive Access after 365 days of no access; Deep Archive after N days (optional) - based on days since last access, not creation date
- Retention: Indefinite (no automatic deletion, manual cleanup only)
- **Orphan cleanup:** Periodic cleanup by prefix for unreferenced S3 objects (if DynamoDB write fails after S3 upload succeeds) - S3 objects include tags/metadata enabling later cleanup (created_at, job_id, artifact_id, writer_request_id)

**Access Control:**
- Bucket: Private (block all public access)
- IAM permissions: Lambda execution roles have read/write permissions
- Pre-signed URLs: Frontend can request via API Gateway → Lambda (required for payloads >5-10MB, optional for smaller payloads)
