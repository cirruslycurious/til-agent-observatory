# Story 3.1: Decision Event Capture

## Status

Approved

## Story

**As an** AI developer  
**I want** all agent actions captured as structured decision events  
**So that** I can analyze decision-making patterns

## Acceptance Criteria

**Decision Event Definition:**
1. A structured record of a significant agent action relevant to workflow reconstruction (spawn, tool call, artifact read/write, accept/reject, goal formulation, etc.) including actor, rationale summary, inputs, outputs, and pointers to evidence.

**Decision Event Types to Capture:**
2. `manager_goal_formulated`: Manager formulates high-level goal (goal text, reasoning, tokens, cost)
3. `manager_goal_sanitized`: Manager sanitizes goal to remove prescriptive instructions (original goal, sanitized goal, removed phrases)
4. `tool_called`: Worker or sub-worker calls tool (tool name, params, results_summary, reasoning, tokens, time)
5. `sub_worker_spawned`: Worker spawns sub-worker (type, reasoning, inputs provided)
6. `artifact_created`: Sub-worker writes artifact (artifact_id, type, quality_signals)
7. `artifact_consumed`: Worker reads artifact (artifact_id, how used in synthesis)
8. `manager_rejected`: Manager rejects output (iteration, sections_cited, reasoning)
9. `manager_accepted`: Manager accepts output (iteration selected, why chosen)
10. `evaluator_assessed`: Evaluator provides conference predictions (top_3, confidence, reasons)
11. `timeout_occurred`: Sub-worker or Evaluator times out (fallback strategy applied)
12. `cost_guardrail_triggered`: Minimal tool mode activated (budget exceeded)
13. `iteration_completed`: Full iteration cycle done (iteration number, outcome)

**Storage & Retrieval:**
14. All decision events written to DynamoDB using two-table pattern (NOT CloudWatch):
    - `decision_events_by_job`: PK=job_id, SK=timestamp#event_type#seq (for chronological queries)
    - `decision_event_ids`: PK=event_id (for uniqueness/idempotency check)
15. Each event includes: event_type, job_id, timestamp, actor (agent), rationale_summary, inputs_summary, outputs_summary, evidence_pointers
16. Events queryable by job_id for workflow reconstruction (from decision_events_by_job table)
17. Events aggregatable for dashboard analytics
18. UI reads events from DynamoDB (not CloudWatch parsing)

**Separation from Operational Logs:**
19. Decision events: DynamoDB decision_events_by_job and decision_event_ids tables (product analytics)
20. Operational logs: CloudWatch (debugging, errors, performance)
21. Clear separation enforced in Lambda functions

### Data Models

**Decision Event Schema (from architecture/data-models.md):**
```python
{
    "job_id": "String (UUID)",  # Partition key
    "timestamp#event_type#seq": "String",  # Sort key (e.g., "2026-01-12T10:30:15.123Z#tool_called#001")
    "event_id": "String (SHA-256)",  # Idempotency key
    "event_type": "String enum",  # tool_called, sub_worker_spawned, artifact_created, etc.
    "actor": "String",  # manager, worker, sub_worker, evaluator
    "summary": "String",  # Human-readable summary
    "details": "JSON",  # Full event details
    "timestamp": "String (ISO datetime)",  # Event time
    "rationale_summary": "String (max 200 chars)",  # Why this action was taken
    "inputs_summary": "String (max 200 chars)",  # Summary of inputs
    "outputs_summary": "String (max 200 chars)",  # Summary of outputs
    "evidence_pointers": "Array of strings (max 10)",  # Source pointers
    "execution_id": "String (optional)",  # Step Functions execution ID
    "state_name": "String (optional)",  # Step Functions state name
    "iteration": "Number (0-4, optional)",  # Iteration number
    "sub_worker_instance_id": "String (optional)"  # Sub-worker instance ID
}
```

**DynamoDB Table Schema (Two-Table Pattern):**
- **Table 1: `decision_events_by_job`** (chronological queries)
  - **Partition Key:** `job_id` (String, UUID)
  - **Sort Key:** `timestamp#event_type#seq` (String, e.g., "2026-01-12T10:30:15.123Z#tool_called#001")
  - **Attributes:** All event data (event_type, actor, summary, details, timestamp, rationale_summary, inputs_summary, outputs_summary, evidence_pointers, etc.)
- **Table 2: `decision_event_ids`** (uniqueness/idempotency check)
  - **Partition Key:** `event_id` (String, SHA-256 hash)
  - **Attributes:** `job_id`, `sk` (timestamp#event_type#seq), `created_at` (for idempotent reads)
  - **Idempotency:** Write uses `ConditionExpression: attribute_not_exists(event_id)` to prevent duplicates on Step Functions retries
  - **Note:** Storing `job_id` and `sk` in decision_event_ids enables GetItem from decision_events_by_job when event_id already exists
- **Write Pattern:** Atomic write to both tables via TransactWriteItems (decision_events_by_job for chronology, decision_event_ids for uniqueness)
  - **TransactWriteItems ensures atomicity:** Either both writes succeed or both fail (no partial states)
  - **On ConditionalCheckFailedException:** GetItem from decision_event_ids to get {job_id, sk}, then GetItem from decision_events_by_job using PK=job_id, SK=sk to return existing event
- **Query Pattern:** Query `decision_events_by_job` by job_id for workflow reconstruction

**Evidence Pointer Grammar (Standardized Format):**
- **Format:** `{type}:{identifier}[#{fragment}]`
- **Types:**
  - `ddb`: DynamoDB table reference
    - Format: `ddb:{table_name}/{pk}/{sk}` (e.g., `ddb:evaluation_results/550e8400...#iteration#0`)
    - Format: `ddb:{table_name}/{pk}` (e.g., `ddb:artifacts/550e8400...#cfp_extract#v1`)
  - `artifact`: Artifact reference
    - Format: `artifact:{artifact_id}` (e.g., `artifact:550e8400...#cfp_extract#v1`)
    - Format: `artifact:{artifact_id}#path:{json_path}` (e.g., `artifact:550e8400...#cfp_extract#v1#path:data.structure_requirements`)
    - Format: `artifact:{artifact_id}#candidate:{k}#span:{start}-{end}` (e.g., `artifact:550e8400...#draft#v1#candidate:0#span:10-50`)
  - `web`: Web search result
    - Format: `web:{search_id}#result:{n}` (e.g., `web:search_123#result:0`)
  - `conf`: Conference data reference
    - Format: `conf:{conference}#rules` (e.g., `conf:black_hat#rules`)
    - Format: `conf:{conference}#abstract:{id}` (e.g., `conf:black_hat#abstract:bh_2023_042`)
  - `s3`: S3 object reference (for large blobs)
    - Format: `s3://{bucket}/{key}` (e.g., `s3://scratch-artifacts/550e8400.../full_artifact.json`)
    - Format: `s3://{bucket}/{key}#L{start}-{end}` (e.g., `s3://scratch-artifacts/550e8400.../full_artifact.json#L10-50`)
- **Rules:**
  - All identifiers must be URL-safe (allowed chars: `a-zA-Z0-9`, `-`, `_`, `#`, `/`, `:`, `.`)
  - `:` is used as type separator (required)
  - `#` is used as fragment separator (optional)
  - Fragment is optional
  - Max 200 chars per pointer
  - Max 10 pointers per event

  ```json
    "next_token": "optional pagination token"
  ```

  ```python
          actor: Agent that performed action (manager, worker, sub_worker, evaluator)
          sub_worker_instance_id: Sub-worker instance ID (optional)
      
      Returns:
          event_id: Generated event ID (for idempotency checks)
      """
  ```

**Event Type Enums:**
- `manager_goal_formulated`: Manager formulates high-level goal
- `manager_goal_sanitized`: Manager sanitizes goal to remove prescriptive instructions
- `tool_called`: Worker or sub-worker calls tool
- `sub_worker_spawned`: Worker spawns sub-worker
- `artifact_created`: Sub-worker writes artifact
- `artifact_consumed`: Worker reads artifact
- `manager_rejected`: Manager rejects output
- `manager_accepted`: Manager accepts output
- `evaluator_assessed`: Evaluator provides conference predictions
- `timeout_occurred`: Sub-worker or Evaluator times out

### Technical Constraints

**Idempotency (Two-Table Pattern):**
- Event ID generation must be deterministic and stable across Step Functions retries
- **Event ID formula:** `sha256(execution_id + state_name + iteration + logical_event_type + job_id + actor + (sub_worker_instance_id or "") + (stable_action_id or ""))`
  - **Stable action IDs:** For event types with natural deterministic IDs, include them in event_id:
    - `tool_called`: Include `tool_invocation_id` from details
    - `artifact_created`: Include `artifact_id` from details
    - `evaluator_assessed`: Include `evaluator_request_id` from details
    - `sub_worker_spawned`: Include `sub_worker_instance_id` (already in formula)
- **Two-table write pattern (atomic via TransactWriteItems):**
  - Use DynamoDB TransactWriteItems for atomic writes to both tables:
    - Put to `decision_events_by_job` table: PK=job_id, SK=timestamp#event_type#seq (chronological)
    - Put to `decision_event_ids` table: PK=event_id, attributes: {job_id, sk (timestamp#event_type#seq), created_at} with ConditionExpression: `attribute_not_exists(event_id)` (uniqueness check)
  - **TransactWriteItems ensures atomicity:** Either both writes succeed or both fail (no partial states)
  - **On ConditionalCheckFailedException:** GetItem from decision_event_ids to get {job_id, sk}, then GetItem from decision_events_by_job using PK=job_id, SK=sk to return existing event
- **Seq Generation (Atomic Counter Pattern):**
  - Counter key: `f"{job_id}#{actor}"` (e.g., "550e8400...#manager")
  - Store counter in `generation_metrics` table: PK=job_id, SK=`seq_counter#{actor}`
  - Use DynamoDB UpdateItem with `ADD seq :one` and `if_not_exists(seq, :zero)` (atomic increment with clean initialization)
  - Return new seq value from UpdateItem response
  - **Note:** Hot partition risk if job has very high event throughput (>100 events/second per actor), but typical jobs have 20-50 events total (not a real problem)

**Separation of Concerns:**
- **Decision Events:** DynamoDB `decision_events_by_job` and `decision_event_ids` tables (product analytics, workflow reconstruction)
- **Operational Logs:** CloudWatch Logs (debugging, errors, performance)
- Clear separation enforced: Decision events NEVER go to CloudWatch, operational logs NEVER go to DynamoDB

**Performance:**
- Decision events are append-only (high write volume, ~20-50 events per job)
- Query pattern: By job_id (partition key) for workflow reconstruction
- No GSI needed (query by job_id is sufficient)
- Consider pagination for jobs with many events (>100 events)

**Event Size Limits:**
- `summary`: Max 500 chars
- `rationale_summary`: Max 200 chars
- `inputs_summary`: Max 200 chars
- `outputs_summary`: Max 200 chars
- `evidence_pointers`: Max 10 pointers (each max 200 chars)
- `details`: JSON object - **Hard limit: 10KB** (enforced validation)
  - Always include `details_hash`: `sha256(json.dumps(details, sort_keys=True))` (deterministic hash for integrity verification)
  - Always include `details_truncated`: `true` if details > 10KB, `false` otherwise
  - If details > 10KB: Store large blob in S3, replace details with summary + S3 pointer in evidence_pointers
  - S3 key format: `decision-events/{job_id}/{event_id}/details.json`
  - Always include `details_s3_pointer` in evidence_pointers when truncated (for full fidelity replay)
  - DynamoDB item limit: 400KB total (details < 10KB ensures room for other attributes)
