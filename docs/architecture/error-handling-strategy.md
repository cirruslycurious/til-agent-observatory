# Error Handling Strategy

## General Approach

- **Error Model:** Structured error responses with error codes
- **Exception Hierarchy:** Base exception classes per component type
- **Error Propagation:** Errors bubble up with context, logged at each level

## Idempotency & Replay Protection

**Critical Requirement:** Step Functions retries and SQS duplicate deliveries must not create duplicate data.

**Idempotency Keys:**

1. **Decision Events:**
   - `event_id = sha256(job_id + actor + event_type + seq + timestamp_bucket)`
   - `seq`: Monotonic sequence number per `job_id + actor` (centrally generated by Manager/Worker, not by sub-workers independently)
   - `timestamp_bucket`: Rounded to nearest second to handle retries within same second
   - **Alternative (if Step Functions state available):** Include `state_name` or `stepfn_state_id` in hash for additional uniqueness
   - Write uses `ConditionExpression: attribute_not_exists(event_id)`

2. **Artifacts:**
   - `artifact_id = job_id + "#" + task_id + "#" + artifact_version`
   - Write uses `ConditionExpression: attribute_not_exists(artifact_id)`
   - Version increments on retry with different content

3. **Evaluator Requests:**
   - `evaluator_request_id = job_id + "#iteration#" + str(iteration)`
   - SQS message deduplication ID uses this key
   - Write uses `ConditionExpression: attribute_not_exists(evaluator_request_id)`

4. **Job Creation:**
   - `job_id` is UUID (globally unique)
   - Write uses `ConditionExpression: attribute_not_exists(job_id)`

**Replay Handling:**
- All DynamoDB writes use `ConditionExpression` to prevent duplicates
- Retry logic checks for existing records before writing
- Duplicate write attempts logged as `duplicate_write_attempt` events (non-blocking)

## Concurrency Limits & Rate Limiting

**Step Functions:**
- **Max concurrent executions:** 50
- **Execution timeout:** 10 minutes per job
- **Queue behavior:** If at capacity, enqueue to SQS `job-queue`
- **Backpressure:** Reject new requests with 503 Service Unavailable if queue is full (>100 queued jobs)

**Lambda Concurrency:**
- **Manager:** Reserved concurrency = 10
- **Worker:** Reserved concurrency = 20
- **Sub-workers:** Shared remaining concurrency (account limit - reserved)
- **Evaluator:** Reserved concurrency = 5
- **API Gateway Lambdas:** No reserved concurrency (use account default)
- **ws-broadcast:** No reserved concurrency (burst handling)

**API Gateway Rate Limiting:**
- **Global:** 100 requests/minute per IP (all endpoints)
- **/generate specific:** 10 generations/minute per IP (Lambda guard, additional to API Gateway)
- **Backpressure behavior:**
  - If Step Functions at capacity: Enqueue to SQS, return `202 Accepted` with `job_id` and `job_read_token`
  - If SQS queue full (>100 queued jobs): Return `503 Service Unavailable`
  - If rate limit exceeded: Return `429 Too Many Requests` with `Retry-After` header
- **Client behavior on 202 Accepted:**
  - Client should immediately open WebSocket connection using `job_id` and `job_read_token`
  - Client should poll `/status/{job_id}` as fallback if WebSocket connection fails
  - WebSocket provides real-time updates; polling provides resilience

**Cost Guardrail Behavior:**
- If daily cost > $20: Auto-disable `/generate` endpoint (return 503)
- If job cost > $1: Trigger minimal mode (reduce tool usage)
- If job cost > $2: Fail job with `BUDGET_EXCEEDED` error

## Logging Standards

- **Library:** CloudWatch Logs (structured JSON)
- **Format:** JSON with correlation_id, service context, error details
- **Levels:** DEBUG, INFO, WARN, ERROR, CRITICAL
- **Required Context:**
  - Correlation ID: `job_id` for all job-related operations
  - Service Context: Lambda function name, version
  - User Context: `user_session_id` (if available)

## Error Handling Patterns

### External API Errors

- **Retry Policy:** Exponential backoff (3 retries, max 30s delay)
- **Circuit Breaker:** Not implemented for MVP (monitor for future need)
- **Timeout Configuration:** 30s for LLM calls, 10s for web search
- **Error Translation:** Map external errors to internal error codes

### Business Logic Errors

- **Custom Exceptions:** `ArtifactValidationError`, `BudgetExceededError`, `TimeoutError`
- **User-Facing Errors:** Structured JSON with error code and message
- **Error Codes:** HTTP status codes + custom codes (e.g., BUDGET_EXCEEDED, VALIDATION_FAILED)

### Data Consistency

- **Transaction Strategy:** DynamoDB conditional writes for idempotency
- **Compensation Logic:** Deterministic fallbacks for timeouts
- **Idempotency:** All writes use ConditionExpression to prevent duplicates
